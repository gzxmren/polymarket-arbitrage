🐋 核心发现① ·"重点关注"鲸鱼名存实亡

数字对比

whales.is_watched=1（重点关注名单）292
07-data/whale_states/ 实际JSON文件数18
重点关注里 changes_count=0（从无成交记录）216 个 (74%)
concentration_history 近7天覆盖的钱包数106 个 (36%)

根因

鲸鱼JSON状态文件由 update_whale_states.py 每6h刷新，但它的发现逻辑来自 whale_tracker_v2.py 的"近期活跃交易扫描"——完全不读取 is_watched 字段。 后备的"高价值鲸鱼占位"逻辑按 total_volume DESC 排序，也不优先重点关注名单，且每轮只补20个。

结果：is_watched 这个字段只在下游消费时被读取（选信号候选、UI展示、写concentration_history的判断条件）， 从未在JSON刷新源头被用来决定"该追踪谁"——"重点关注名单"和"实际被持续追踪的名单"是两套互不相交的东西。

影响：项目定位是"大户行为追踪平台"（CLAUDE.md 开篇定义），重点关注名单理应是最高优先级的追踪对象。 现状是其中3/4根本没有任何交易行为被记录——不是这些鲸鱼不活跃，而是系统从未去看过他们。 whale_following 信号生成依赖 changes 表，这一覆盖率缺口直接限制了能产生信号的鲸鱼池子大小。
📈 核心发现② · 价格快照覆盖率不足，且与今天修的"分页缺陷"是两个不同层面的问题
changes 表里鲸鱼实际交易过的不同市场数9,158
其中从未出现在 daily_price_snapshots 的市场数5,480 (60%)

今天复查并修复的"分页缺陷"（详见 docs/DATA_QUALITY_FOLLOWUP_2026-06-21.md）解决的是 "已经在采集范围内的市场，某几天数据缺失/不完整"。这里是更上一层的问题： snapshot_daily_prices.py 按 volume24hr 排序只抓 Gamma API 的 top ~2000 活跃市场， 长尾/低交易量市场天然不在采集范围——鲸鱼一旦在这些市场交易，无论时间窗口对不对，从源头上就没有价格历史可用。

影响：这是比黑名单覆盖不全更大的天花板——即使 whale_following.py 的可结算判定逻辑做得再精确， 60%的鲸鱼交易市场依然因为"压根没采集过"而无法生成可结算信号。

🔄 changes 表的两个细节问题

752条完全重复行

同 wallet+market+timestamp+change_amount 完全一致的行有752条。需要确认是同一笔交易被插入了两次（去重缺失）， 还是确实存在同一时间戳的多笔独立交易（小概率但可能，取决于上游API时间戳精度）。未在本次范围内继续深挖，列为待办。

BUY:SELL = 21k:5k（80/20失衡）

changes 表里 BUY 20,988条，SELL 仅5,000条。可能是真实市场行为（鲸鱼买入多于卖出）， 也可能是SELL方向的检测逻辑存在系统性漏报（例如清仓到0的情形未被正确归类）。建议下次排查时核对 sync_changes.py 对SELL的识别条件。

🔧 data_sync.py vs data_sync_v2.py — 本次可以下结论了

CLAUDE.md 长期标注"两个sync实现并存，权威性不明确"。核查 scheduler.py:14,26-30， APScheduler 的 data_sync job 唯一导入的是 from .data_sync import DataSyncService。 全仓搜索 data_sync_v2 的引用，只有一个一次性脚本 backfill_concentration.py 在用， 没有任何cron/scheduler路径会触发它。

结论：data_sync.py 是唯一生效的版本，data_sync_v2.py 应视为废弃代码， 建议后续归档到 99-archive/ 以减少误读风险（本次未做改动，留待用户决定）。

结论
数据库本身干净健康，表层的"空表/断路"类问题（6/7报告的主要槽点）这次也基本看到已解决。
但这次摸到了更深一层、更隐蔽的问题："重点关注"名单和实际被追踪的对象是两套数据， 鲸鱼实际交易的市场里六成从未被采过价——这两条共同限制了信号生成的源头， 使得"先验证再投"所需的样本积累速度，比代码本身的健康度看起来要慢得多。

建议下一步：把"is_watched 优先刷新"接入 update_whale_states.py 的发现逻辑，是性价比最高的单点改动—— 不改变任何策略逻辑，只是让系统真正去看它自己说要重点关注的对象。
