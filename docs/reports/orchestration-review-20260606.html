4 发现的问题（按优先级排序）

  • 🔴
    P1 · backup-configs 连续失败 5 次，无告警 P1 每天 03:00 运行，连续 5 天报错，但配置了 failureAlert: null——你完全不知道它在失败。备份失败意味着配置损坏后无法恢复。
  • 🔴
    P1 · 所有 Polymarket 任务都没有配置失败告警 P1 monitor-lite / sync-changes / update-whale-states / daily-price-snapshot 这些核心任务的 failureAlert 全是 null。哪天 API 挂了、网络断了，你什么通知都收不到，数据悄悄停止更新，回测用的全是过期数据。
  • 🟡
    P1 · 信号追踪链断路：推了多少信号，几个对？完全不知道 P1 signals / signal_results / whale_performance 三张表全空。当前系统只是把信号推到 Telegram，但没有"推送→结果→评分"的闭环。不知道 polycop 信号准确率是多少，无法筛选"有效鲸鱼"。这是从监控到盈利最大的断点。
  • 🟡
    P2 · polymarket-monitor-v2 已关闭 6 周，原因不明 P2 完整监控引擎（v2）在 2026-04-22 之后没有跑过，被 lite 版替代。lite 版只需 3.3 秒（vs v2 的 184 秒），但可能采集的字段/深度不同。需要确认 lite 版是否采集了 v2 版的所有必要字段，否则可能有数据盲区。
  • 🟡
    P2 · P0-B 周复验在系统 crontab，不在 OpenClaw（今天刚加）P2 刚加的 weekly_pzero.sh 用系统 crontab 调度，没有 Telegram 推送结果、没有失败告警、没有 AI 上下文。运行了没有是未知的。应迁移到 OpenClaw cron。
  • 🟡
    P2 · 07-data 文件不做轮转，289 MB 且仍在增长 P2 虽然有 cleanup 任务，但 whale_report_*.json 多版本留存（每次 monitor-lite 运行都新建一个 1-2 MB 的文件），加上 whale_states/ 目录，合计 2200+ 文件、289 MB。长期来看磁盘和 DB 查询性能都有隐患。
  • 🔵
    P3 · 两套调度混用，难以统一管理 P3 OpenClaw cron + 系统 crontab 两套并存，如果某个任务挪到了一个，另一个忘记删，就会重复运行。建议把 Polymarket 相关任务全部迁入 OpenClaw 统一管理。
  • 🔵
    P3 · sync-changes 频率（90 分钟）与 monitor-lite（60 分钟）未对齐 P3 monitor-lite 每 60 分钟产生新 whale_report，但 sync-changes 每 90 分钟才把流水写入 changes 表。存在 30 分钟的数据延迟窗口。对于回测来说影响不大，但若将来做实时决策则会引入延迟。

5 优化建议（面向盈利目标）

🔴 立即要做（P1）

🔔
为核心任务加上失败告警 在 OpenClaw cron 里，为 sync-changes、update-whale-states、daily-price-snapshot 加上 failureAlert 配置，推送到你的 Telegram。这样任何数据断流，你第一时间知道。预计 5 分钟配置。
🛠️
修复 backup-configs 脚本 连续 5 天失败，查 ~/.openclaw/cron/runs/433cff3d-*.jsonl.migrated 里的错误信息，找到原因并修。之后加失败告警。
🔗
接通信号追踪链（P1，对盈利最关键） 这是从"监控系统"变成"有记忆的盈利系统"的最重要一步。具体：每次 polycop 扫到信号时，把信号写入 signals 表；一周后自动查结果，写入 signal_results；每月统计鲸鱼准确率，写入 whale_performance。这样就能知道"哪个鲸鱼值得跟"。

🟡 近期可做（P2）

🤖
把 P0-B 周复验迁移到 OpenClaw cron 把今天加的 weekly_pzero.sh 从系统 crontab 改为 OpenClaw 任务，这样：① 结果自动推 Telegram；② 失败会告警；③ 有任务日志可查。只需在 OpenClaw 里新增一个 cron 任务，然后从系统 crontab 删掉那条。
📋
确认 monitor-lite vs v2 的数据覆盖差异 对比 polymarket_monitor_lite.py 和 polymarket_monitor_v2.py 写入哪些字段，确认 lite 版是否覆盖了 v2 的所有采集内容。如果有缺失，补回来或重开 v2。
🗂️
给 whale_report 加文件保留期限 建议只保留最近 7 天的 whale_report_*.json（每天约 3-4 个，每个 1-2 MB），7 天前的自动删除。在 cleanup 任务里加一行即可，可以节省 ~200 MB 磁盘。

🔵 长期可考虑（P3）

🔄
统一到 OpenClaw，去掉系统 crontab 的 Polymarket 条目 Leaderboard 跟踪（当前在 crontab）可迁入 OpenClaw，享受 Telegram 推送和告警。统一管理更清晰。
⏱️
把 sync-changes 频率从 90 分钟改为 60 分钟 与 monitor-lite 对齐，减少数据延迟。sync-changes 单次 5 秒，对系统无压力。

调度层不是孤立的技术问题，它直接决定我们能不能从"有监控"走向"有盈利"。

最关键的断点：当前系统在"信号生成 → 信号追踪"这一步断了。我们推了 Telegram 信号，但从不记录"这个信号后来对了没有"。没有这个数据，就无法知道哪个鲸鱼值得跟，也就无法筛选出有效信号源——而这恰恰是 C0 逆势/H6 微仓等策略能否在生产环境中应用的前提。

一句话结论： 采集层已经健壮，每天在认真积累数据。但从"信号推送"到"学习哪些信号有效"这条链是断的。 接通这条链（signals → signal_results → whale_performance），是调度层能为盈利目标贡献的最高价值单件事。
