## 二、🔴 反面教材:`PolymarketBTC15mAssistant` 的"概率"在数学上是坏的

**这一节值得单独记,因为它算出来的数字看起来完全合理。**

`src/engines/probability.js`(全文 59 行)的做法:

```js
let up = 1, down = 1;
if (price > vwap) up += 2;           // 价格在均线上方
if (vwapSlope > 0) up += 2;          // 均线上行
if (rsi > 55 && rsiSlope > 0) up += 2;
if (macd.hist > 0 && macd.histDelta > 0) up += 2;
if (heikenColor === "green" && heikenCount >= 2) up += 1;
const rawUp = up / (up + down);      // ← 这个被当成"概率"
```

`src/engines/edge.js` 直接拿它减市场价:
```js
edgeUp = modelUp - marketUp;         // 分数比 − 真实概率
```

🔴 **`up/(up+down)` 是分数比,不是概率。** 全部指标看涨时它给出 0.917,
但**没有任何东西保证"分数比 0.917"对应"91.7% 的实际发生频率"** ——
零校准、零历史验证。⇒ **拿一个没有概率含义的数减去真实市场概率,得到的 "edge" 是假的。**

### 🔴 第二个错:时间调整的方向是反的

```js
adjustedUp = 0.5 + (rawUp - 0.5) * (remainingMinutes / windowMinutes);
```
**剩余时间越少,它把概率越往 0.5 拉。** 而现实相反:只剩 1 分钟且 BTC 已经涨了,
"涨"的概率应接近 1 而非接近 0.5。**它把最确定的时刻当成了最不确定的。**

### ⇒ 对我们的意义

这正是本项目那套判据存在的理由:**这些数字算得出来、落在 [0,1]、能比大小、看着合理,而它是错的。**
⛔ 我们的 spec §7 规则:任何"模型概率"必须先过**校准检验**(说 60% 的那些,实际赢了多少次),
才允许拿去和市场价相减。**没校准过的模型价 ⇒ 算出的 edge 一律不可采信。**

## 三、⭐⭐ 最值钱的反向启发:三个作者都把"两腿和"当噪声除掉了

`edge.js` 里这一行:

```js
const sum = marketYes + marketNo;
const marketUp = marketYes / sum;    // ← 归一化
```

作者**遇到了 "UP 价 + DOWN 价 ≠ 1"**,处理方式是**除掉它、当噪声**。

而"两腿和 ≠ 1"本身就是**无风险套利空间**:和 < 1 时两边全买锁定利润,和 > 1 时反向。

**三个仓库、三个作者,全部在做「预测方向 → 下注」,没有一个在看两腿和。**

这只可能是两种情况之一:
1. 那个机会早被做市机器人吃干净了(所以没人提),或
2. 大家都忙着预测方向,根本没往这边看。

🔴 **哪一个是真的,采一段盘口数据就知道** —— 而这是最便宜的一枪,判据还极硬
(两腿最优价之和 vs 1,黑白分明,不需要任何模型)。

## 四、✅ 可直接借鉴的三样(已并入 spec)

### 4.1 ⭐ Chainlink 数据的**第二条获取路径**(解决 spec 一个悬着的假设)

`PolymarketBTC15mAssistant` 除了走 Polymarket WS,还能**直接从 Polygon 链上读 Chainlink**:
```
POLYGON_RPC_URLS  = https://polygon-rpc.com,https://rpc.ankr.com/polygon
POLYGON_WSS_URLS  = wss://polygon-bor-rpc.publicnode.com
```
实现见 `src/data/chainlink.js`(130 行 HTTP)与 `chainlinkWs.js`(166 行 WSS)。

🔴 **这解决了 spec §2.4 里那个未验证的假设**:我们用的免费 RTDS
(`wss://ws-live-data.polymarket.com`)推的值,**是不是官方结算真正引用的那个值**?
⇒ 用**链上直读做交叉验证**即可确认,这是独立的第二来源。
⚠️ 注意 README 原话:Polymarket WS 那路是 "**same feed shown on the Polymarket UI**",
即 UI 与 WS 同源 —— 所以**它不能自证**,必须靠链上这条独立路径。

### 4.2 ⭐「没机会就不动手」的四条闸(`5min-btc` 的 `execution_safety`)

| 条件 | 动作 |
|---|---|
| 盘口价差 > 0.03(3 分钱) | 跳过 |
| 最优档名义额 < $30 | 跳过 |
| 报价陈旧 > 8 秒 | 跳过 |
| 心跳陈旧 > 15 秒 | 跳过 |
| 连续 DNS/API 错误 ≥ 3 次 | 跳过 |

⭐ 这正是用户要的那个性质(「有空间就操作,没有就不操作,不会造成损失」)的**落地形态**。
⚠️ 但数值(3 分 / $30 / 8 秒)是他们拍的,**我们要用自己的实测分布重定**(spec §7 规则 2)。

### 4.3 ⭐ 执行层不必从零建 + 两个现成的工程决定

- **下单**:`py-clob-client`;配套止损/止盈/移动止损/时间退出/优雅停止/心跳/对账/看门狗
  (`polymarket-hl-strategy/src/live/pm_live_trade_runner.py` 等)
- **多盘并存怎么选**:维护 `prev / current / next / next2` 四个候选槽,取 `closest_valid`
  ⇒ **这回答了 spec §6 采样设计里「一次盯几个盘」那个悬着的问题**
- **结算前强制平仓**:`exit_before_sec: 20`(避开最后时刻的不确定)

⇒ **阶段二的成本估计要下调**:原 spec 写「执行层从零建」,实际有成熟轮子可用。
