## 2. 🔴 价格源:**不是币安,是 Chainlink 60 秒 TWAP**(2026-09-06 查清,全部实测)

### 2.1 结算规则(Gamma 元数据原文)

```
resolutionSource : https://data.chain.link/streams/btc-usd-twap-60s-streams
cryptoMarketConfigId : btc-15m-twap-60
cryptoMarketConfig : {"asset":"btc","duration":"15m","twapEnabled":true,"twapLookbackSeconds":60}
```
> "This market will resolve to **Up** if the **time-weighted average price (TWAP) of Bitcoin, generated by
> Chainlink**, of the time range specified in the title is **greater than or equal to the price at the
> beginning of that range**. Otherwise **Down**. …this market is about the price according to the TWAP
> Chainlink data stream for the asset pair BTC/USD, **not according to any other sources or spot markets**."

⇒ 🔴 **用币安做"真值"是错的前提**,末句明文排除一切现货市场。
⚠️ 背景(subagent 查、多信源交叉):**2026-08-07 起**这类盘才从单点快照价改为 60 秒 TWAP,
官方理由是**防止结算瞬间被狙击** ⇒ 路 A(抢跑)正是这次改制针对的对象。

**实测确认**:当前在跑的 `btc-updown-15m-*` 全部 `config=btc-15m-twap-60`(样本 2 个,一致)。
⚠️ 配置表里另有非 TWAP 的 `btc-15m`,推测是改制前遗留 —— **V0 必须逐盘校验 config,不许假定**。

### 2.2 ✅ 数据源已验证可用(免费、无需凭证)

| | |
|---|---|
| 端点 | `wss://ws-live-data.polymarket.com`(Polymarket RTDS) |
| topic | `crypto_prices_twap_sixty`(60s)/ `crypto_prices_twap_thirty`(30s) |
| filters | `"{\"symbol\":\"btc/usd\"}"` —— **紧凑 JSON 字符串,无空格** |
| 保活 | 每 5 秒发文本帧 `PING` ⚠️ **这条是「读的」不是「测的」** —— 官方文档要求,但二审压测发现持续收数据时 240 秒不发也没断,其必要性未被证实。照发(成本≈0),但证据等级不许标成实测 |
| 报文 | `payload:{symbol,value,full_accuracy_value,timestamp,window_s}`;`full_accuracy_value` 是 E18 定点(÷10^18) |
| 频率 | **实测每秒 1 点**(间隔中位 1000 ms),`window_s=60` |
| 历史 | 连上时首条是 `payload.data[]` **历史快照,实测覆盖 1.0 分钟** |

🔴 **六条陷阱,全是实测踩到的**:
1. **文档说 "There is no snapshot, history, or replay" —— 是错的**,实际连上就给 1 分钟历史。
   ⇒ 文档不可全信,任何字段都要 dump 实物核对。
2. **首条消息与后续消息结构不同**(首条 `payload.data` 是数组,后续 `payload` 是单点)——
   直接按文档示例解析会 `KeyError`。V0 必须两种都处理。
3. **实际有三种消息形态,不是两种**(二审补):订阅请求后**先回一条空字符串**(订阅确认帧),
   `json.loads()` 不加保护会先炸在这条上。⇒ V0 必须处理:空帧 / `data[]` 快照 / 单点更新。
4. **现货 topic 的 symbol 格式不同**:TWAP 用 `btc/usd`(带斜杠),现货 `crypto_prices` 必须用
   `btcusdt`(不带斜杠)。二审实测把 TWAP 的 filter 直接复制到现货 topic,**12 秒零数据、静默无报错**。
   ⇒ ⛔ V0 不许两个 topic 共用同一个 filter 字符串。
5. **`full_accuracy_value` 的 E18 编码只在 TWAP topic 成立**;现货 topic 里它就是 `value` 的字符串形式
   (未乘 1e18)⇒ 共用解析代码会静默算错 18 个数量级。
6. ⚠️ **topic 选错会静默拿到错的东西**:`crypto_prices`(无 twap 后缀)推的是 `btcusdt` **现货**,
   正是结算规则明文排除的那类。**V0 必须断言 `payload.symbol=="btc/usd"` 且 `window_s==60`。**

### 2.3 ⭐ 基差:现货当代理会差多少 —— **是滞后效应,不是固定偏移**(二审更正)

我(75 秒样本)测得中位 **−1.45 bp**,且**全部为负**,据此写了"系统性偏移不是随机噪声"。
🔴 **二审独立复现推翻了这个表述**:它用同样方法采约 130 秒,中位 **+1.41 bp**(符号相反),
且样本前段为负、后段转正,**翻转精确对应现货价格自身先涨后跌的走势反转**。

⇒ **正确的解读**:基差本质是 60 秒滑动平均相对现货走势的**滞后效应** ——
谁涨谁跌决定它此刻是正是负,**方向不固定、不可预测**。我原来那句"系统性偏移"是
在一段单向行情里只量了一组就下的结论(本项目反复发作的"只量一组就盖章")。

**站得住的只有量级**:两次独立测量的 |基差| 都在 **3 bp 以内**,
而 taker 手续费 p=0.5 时 **175 bp**、盘口价差 1 分钱 ≈ **170 bp** ⇒ **比成本小两个数量级**。

⚠️ 且两次都只采了平静行情。TWAP 是 60 秒平均 ⇒ **剧烈波动时滞后必然放大**,没测。
⇒ 结论:**判决路径一律用 TWAP,现货只用于监控,不进任何判决**。
这个决定不因符号问题动摇 —— 反而更该坚持,因为基差既不稳定、方向又不可预测。

## 3. 🔴 两条路各测什么(二审:此节在 09-06 重写时**整节丢失**,此处补回并重新定义)

更糟的是:初版本有这一节,是我重写时弄丢的。补回时按二审意见做了**重新划界**。

### 3.1 ⭐ 先把界划对:原来的"抢跑 vs 持续偏差"分法是错的

TWAP 结算改变了机会的结构。**结算 = end 时刻的 60 秒 lookback TWAP**(§2.4)⇒
在 `end − 60s` 之后,结算值的**一部分已经落定**(那几秒的价格已经进入平均),
且随时间推移,结算 TWAP 的不确定性**单调下降、并且是可以算的**。

⇒ 由此产生的机会("比市场更早算出正确概率")**不需要速度优势,它需要的是算得对** ——
**它属于路 B,不属于抢跑**。原稿把它混在路 A 里,会得出没有分辨力的判决。

**重新划界后**:

| | 测什么 | 需不需要速度 | 我们的先验 |
|---|---|---|---|
| **路 A · 执行速度** | Polymarket **盘口**对新信息的反应延迟,能否在别人之前吃到 | 🔴 需要 | **低**(见 3.2) |
| **路 B · 定价质量** | 给定当时**所有公开信息**(含已落定的那段 TWAP),市场价对不对 | 🟢 不需要 | 未知,是主攻方向 |

### 3.2 路 A · 执行速度 —— 可执行定义 + 诚实的先验

⚠️ **先验很低,原因是读出来的**:官方 2026-08-07 改制的**明确目的**就是
"逼迫操纵者把价格压在阈值一侧连续维持 30~60 秒"(§2.1)。
⇒ 单次 tick 对 60 秒均值的权重被**结构性稀释**,传统"看到现货跳一下就抢"打的是均值里
几乎可忽略的一段。**这是官方设计要达到的效果,不是我的推测。**
⚠️ 但"先验低"不等于判死 —— 用户拍板两条都测,**照测,只是不许把它当主攻**。

**可执行定义(先写死)**:
- **触发事件**:60s TWAP 相对**该盘起点 TWAP** 的偏离,在 Δ 秒内变化超过 X bp
  (Δ、X 由 V1 的成本分布反推:**至少要大到能覆盖单边总成本**,否则抢到也不赚)
- **被测量**:从触发时刻起,Polymarket 盘口中间价收敛到新公允价的**滞后分布**
- **判生死**:`滞后中位数` vs `我们的热连接往返 p95`(V2)。
  ⛔ 前者 < 后者 ⇒ 判「路 A 死」,不许再用任何理由复活。
- **公允价怎么算**:需要一个"给定当前 TWAP 轨迹与剩余时间,结算为 Up 的条件概率"模型。
  🔴 **这个模型目前不存在,是路 A 的硬前置** —— 而它一旦存在,**路 B 也直接用它**。

### 3.3 路 B · 定价质量 —— 主攻方向

**问题**:给定当时所有公开信息,市场报价与"正确概率"差多少?差在哪个价位、哪个时点?

⭐ **TWAP 结构给了一个别处没有的便利**:结算规则是**完全确定的数学**
(end 时刻 60s TWAP ≥ start 时刻 60s TWAP),不像事件盘那样依赖主观判断。
⇒ "正确概率"原则上可由 BTC 价格过程算出,不必靠历史频率去估。
⚠️ 但这需要 3.2 里那个条件概率模型 ⇒ **两条路共用同一个硬前置**。

**因变量**:实际结算结果(Gamma 给,不需要我们重建 TWAP)。
**红线**:偏差 > 同价位桶的单边总成本中位(§7 规则 3)。

⚠️ **二审查证并排除了一条致命顾虑**:我担心"这类盘的报价本来就是做市商按 TWAP 模型算出来的,
定价偏差压根不存在"。二审实测市场 `marketMakerAddress` **字段为空**(不是链上 AMM),
且流动性来自开放式打分激励(任何人挂单都能分钱,§2.5)
⇒ 报价是众多逐利者报出来的,**不是被钉死在某个官方模型的公允值上** ⇒ 路 B 的前提成立。

## 4. 标的定义(实测)

`btc-updown-15m-<unix_ts>`,例 `btc-updown-15m-1788595200` = "Sep 5, **4:00AM-4:15AM ET**"。
slug 尾部时间戳 = **窗口开始时刻(UTC)**;`endDate` = 开始 + 900 秒。
每 15 分钟一个 ⇒ 一天 **96** 个 ⇒ **一周约 672 个已结算样本**。

**生命周期(实测一个跑完的盘,773 笔成交)**:

| 阶段 | 实测 |
|---|---|
| 开盘前 | 最早成交在锚点 **−29 分**,稀疏(每分钟 0~7 笔) |
| 窗口内 0~+15 分 | 密集,每分钟 **22~102 笔** |
| 结算后 | 🔴 **流动性归 0,盘口只剩 `None/0.001`** |

**三个相邻盘同时并存**(实测):已结算($6,767 成交 / 流动性 $0)、正在跑($6,753 流动性 / 盘口 0.53-0.54)、
未开盘($15,632 流动性 / 盘口 0.50-0.51)。

⚠️ 记账:我 2026-09-04 报过「15m 单盘成交 $1,091」,那是**盘没跑完时**的快照;完整生命周期 **$6,767**。旧数作废。

### 🔴 由标的导出的三条硬约束

1. **盘口与 TWAP 都过期即焚** —— 结算后盘口消失且无历史接口;RTDS 只给 1 分钟快照。
   ⇒ **只能实时往前采,不采就永远没有。这是整件事唯一有时效性的部分。**
   (可选交叉源:第三方 `pmdata.dev` 售 2026-08-01 起的 TWAP Parquet,需 API key。**不作为主源**,
   仅备将来交叉验证;第三方数据真实性我们无法独立验证。)
2. **交易早于窗口开始**(锚点前 29 分钟已有成交)⇒ 任何"取某时刻价格"**必须写明相对锚点的偏移**,
   ⛔ 不许含糊说"开盘价"。
3. **结算 85 秒内自动完成**(`automaticallyResolved:true`),但 UMA 争议窗口理论上存在
   ⇒ V0 要防"结算未终局就被采成定局"。

## 5. 🔴 交易成本(**公式已知,不必靠测量猜**)

```
taker 手续费 = shares × 0.07 × price × (1 − price)        # feeSchedule: rate=0.07, takerOnly=true
```
实测字段:`feeType:"crypto_fees_v2"`,`feeSchedule:{"exponent":1,"rate":0.07,"takerOnly":true,"rebateRate":0.2}`

- p=0.5 时 **1.75% 名义额**(最贵),向两端衰减到 0 ⇒ **随价位变化**
- **maker(挂单被动成交)零手续费,另得 20% 返佣**

⇒ **单边总成本 = 半价差 + 冲击 + 手续费**。
🔴 我 2026-09-05 的成本定义只写了"半价差 + 冲击",**漏了手续费**,会把红线定得太松 ⇒ 已修正。
⚠️ 因手续费与价差**都在 p=0.5 附近最贵**,§7 的红线**必须按价位桶比**(见 §7 规则 3)。

### 🔴 最小报价单位是**价位相关**的(二审实测,原稿完全没提)

二审现场实测:价格接近 0.5 的在跑市场 `tick = 0.01`;已结算到极值(1/0)的市场 `tick = 0.001`
⇒ **tick 随价格档位动态变细**。

⇒ 这对**路 B 在价格尾部(接近 0 或 1)的校准精度有直接影响** —— 而尾部恰恰是知情交易最可能扎堆处。
⛔ V1 的成本模型**不许隐含假设全程统一 tick**,必须按档处理。
⚠️ 记账:我在 §2.1 dump 元数据时**看到过** `orderPriceMinTickSize: 0.001`,却没写进 spec、没做任何分析
—— 又一次「记录了事实但没接到使用的那一头」。

⭐ maker 零费这一点直接影响阶段二:**挂单 vs 吃单的成本结构天差地别**,阶段二设计时必须当作首要变量。

| **Polymarket 盘口**(整档 book) | 每盘覆盖锚点 **−30 ~ +15 分**,窗口内加密;⛔ 不许只存最优价 | 🔴 只能往前采 |
| **Polymarket 成交** | 同上 | 🟢 可回填(单盘笔数 ≪ 1 万) |
| **结算结果 + config 校验** | 每盘一次;同时记 `cryptoMarketConfigId` 与 `feeSchedule` | 🟢 可回填 |
| **我们的往返延迟** | **热连接**(长连接/WS)口径,≥100 次取分布 | 随时可测 |
| 现货价(btcusdt) | 仅用于监控基差是否漂移 | ⛔ **不进判决路径** |

### 🔴 采样设计必须先写死的四件事

1. **时间戳用哪个 —— 具体机制(二审判定原稿"只提问题没给方案",此处补死)**
   🔴 **两边一律只用服务端时间戳,本机接收时刻只用于诊断、不进任何计算**:
   - Chainlink TWAP:用 `payload.timestamp`(观测时刻),**不用**外层 `timestamp`(发布时刻)
   - Polymarket 盘口:用 `/book` 响应自带的服务端 `timestamp`(ms)
   ⭐ **两者都是服务端时钟 ⇒ 我们到各源的链路延迟不对称被整体消掉**,
   这正是"谁先动"能被回答的前提。
   ⚠️ **残留风险改为:两个服务端之间的时钟偏移**(不再是我们的链路)。
   处置:V0 每轮同时记录 `本机接收时刻 − 服务端时间戳` 的差值序列,
   **两条链路各一条**;若二者差值的**中位数之差**随时间漂移超过 200 ms,判该段数据不可用于路 A。
   ⛔ 不许用 V2 测的"端到端延迟绝对值"去校正不对称 —— 那是两回事。

2. **一次盯几个盘** —— 未开盘/进行中/刚结算多个并存,盯太少漏窗口、太多撞 429 限流(本项目踩过)。
3. **时区** —— 一律 UTC(本项目曾因未设 UTC 虚构过不存在的异常)。
4. **采样要覆盖不同时段** —— 这类盘 24/7 跑,流动性有时段模式;
   V1 的 ≥30 盘**必须跨至少一个完整自然日的不同时段**,否则冻结的成本红线自带时段偏。

### 复用与不复用(⭐ 该抄的要抄)

✅ 复用 `06-tools/monitoring/h6_slippage_probe.py` 的 `walk_book_buy()` / `best_prices()` —— 纯数学,
且**内含一条真金白银的教训**:Polymarket `/book` 的 asks 按价格**降序**、bids **升序**,
最优价在数组**末尾**,不能用 `[0]` 取,必须 `min(ask)`/`max(bid)`。
⛔ **不复用** `eligible_sides()` 的筛选阈值(`VOL24H_MAX=200k`/`DTE_MAX=14天`/`PRICE_MAX=0.85`)——
那是给 H6 长周期慢盘调的,对 15 分钟盘完全不适用。

## 7. 判据框架(🔴 现在写死规则,数值等 V1)

**顺序不许换**:

1. **T0 先定**(§2.4):结算取哪段 TWAP、起点价是什么。**没定死之前不许开始跑任何判决。**
2. **测成本(V1)** —— 产出**按价位桶分组**的单边总成本分布(半价差+冲击+手续费)。
   ⛔ 必须走整档盘口;⛔ 不许用最优买卖价冒充;≥30 盘 × 跨时段。
   🔴 **每盘的采样时刻必须是先写死的固定相对偏移**(二审:留空会让实现者无意中偏向
   流动性最好的时段,使成本系统性偏低、红线定太松):**锚点 −5 / 0 / +3 / +8 / +14 分**,共 5 点。
   ⇒ 这是**时间防火墙的同一条原则推广到成本采样**:取值时刻不许与结果或便利程度相关。
3. **成本一出立即冻结红线** —— 定价偏差必须 **> 同一价位桶的单边总成本中位**。
   ⛔ **按价位桶逐桶比,不许拿两个全局中位数打擂台**(手续费与价差都在 p=0.5 最贵,
   而偏差可能集中在别的价位 ⇒ 全局混合比较会产生 Simpson 式错配)。
   ⛔ 红线冻结后不许再动;⛔ 不许看到偏差结果再定红线。
4. **功效闸先于红线** —— 若随机对照的噪声底比要找的信号还宽,判「无分辨力 / 无判决」,
   ⛔ 不许报证伪。(08-19 栽过:零分布 p95=+4.16% 而赚钱只需 1pp。)
   ⭐ **零分布必须用按天/按小时分块的 block bootstrap**,不许默认样本独立 ——
   15 分钟窗口首尾相连、共享同一条价格路径,且定价偏差可能有时段聚类。
   (初步抽查 59 个连续窗口的**涨跌结果**未见 lag-1 自相关,但**定价偏差本身的自相关没查过**,
   而功效闸关心的是后者。)
5. **三个数必报**:平均 / **中位** / 样本量。⛔ 不许只报平均(V6 实测臂B 平均 −0.112% 而中位 **−100%**)。
6. **🟢 才是风险区 —— "更严审视"的可执行定义(二审:原稿只是形容词)**:
   任一路出现 🟢,**必须**再过这三关才允许写进结论,缺一不可:
   ① **独立 holdout 窗口**:用判决窗之后一段全新数据重跑,红线不变;
   ② **安慰剂检验**:把标的换成同期的**非 TWAP 对照**(或随机打乱窗口标签)重跑,
      安慰剂必须是红的 —— 若安慰剂也绿,说明测的是流程假象不是信号;
   ③ **两种口径互印**:成本与偏差各换一种独立算法重算,结论符号不变。
   ⛔ 三关任一不过 ⇒ 判 🟡 不可采信,不许只报那个绿灯。

### 时间防火墙

⛔ 取价时刻**不许**用与结果相关的变量定义(如"价格收敛到 0/1 时"、"最后一笔成交前 X 分钟")——
本项目为此作废过整个结论(08-10 前视偏差 +11.99pp)。
一律用**相对 slug 锚点的固定偏移**,先写死再采。

### 结算映射要写判据验

`outcomes:["Up","Down"]` 与 `outcomePrices` 按下标对齐(实测样例 `["0","1"]` = 结算为 Down)。
⚠️ 本项目在"字段名看着直白、实际读反"上摔过跟头(`resolved_outcome` 是赔付值不是赢家编号,
读错只让符号静默翻转而结果看着一样合理)⇒ **V0 必须写一条判据,用已知结果的市场验证这个映射。**

## 8. 阶段门

**阶段一 · 测量与判决**(本 spec 主体)
产出:路 A(抢跑)与路 B(持续偏差)各一个判决 + 按价位桶的成本分布 + 容量估计。

**⇒ 进入阶段二的门槛(先写死)**:
1. 至少一条路 🟢,且
2. 该路偏差 **> 同价位桶的单边总成本中位**,且
3. 功效闸通过(block bootstrap 下的噪声底看得见该量级),且
4. **容量测算:按"吃掉单盘 1% 成交额"计,预计毛收益 ≥ $50/天**
   ⚠️ 这个数字是**现在拍的**,依据:低于它则一年不足 $18K,不值得为其建执行层与承担实盘风险。
   ⛔ 它是个**可机械判定**的门,不是形容词 —— 原稿写"值得建执行层"是留给自己的解释空间,已修正。

**任一条不满足 ⇒ 不进阶段二。** 关掉方向是正当结局,本项目已这样关掉过六个候选。

**阶段二 · 实盘**(⛔ 只写轮廓)
已知要解决:下单执行层(项目目前纯 read-only)、资金与仓位、风控熔断、实盘与模拟对账、
以及 V7「我们的单子能不能成交」。
⭐ **建议先做影子盘**(按真实盘口记录"若此刻下单会成交在什么价",不动真钱、不需要执行层)——
**这是我的建议,不是用户的决定,待拍板。**
⚠️ `restricted: true` 字段含义(地域/资格限制?)未查清,阶段二启动前必须单独确认。

## 9. ⛔ 本 spec 不能回答什么

1. **实盘真能赚多少** —— 资金占用、税、对手方反应不在内。
2. **我们一进场对手会不会变** —— 做市商见到稳定对手会调报价;本 spec 测的是**现状**。
3. **结论能维持多久** —— 平台一个月前刚改过结算机制(单点→TWAP),规则本身在变。
4. **能否外推到别的品种/周期** —— 只测 BTC 15m 就只答 BTC 15m。
