# 静默失败错误清单(2026-08-03)

> 按**下次你会看到的症状**组织 —— 因为复发时你看见的是症状,不是错误本身。
> 与 `engineering-pitfalls-2026-07-15`(实验设计 → 假结论)互补:那份讲**数字是假的**,
> 这份讲**系统压根没在干活,但看起来在干活**。

## ⚠️ 共同点(比清单本身更重要)

**这批错误没有一个会报错、崩溃或亮红灯。** 进程正常、日志照打、看板全绿、磁盘在涨。
唯一的异常是某个计数**恒为 0**,而没有人规定过"它不该是 0"。

> **显式失败(抛异常、HTTP 5xx、进程退出)有人管;静默失败(一切正常但产出为 0)没人管。**
> 而静默失败潜伏期极长 —— 这次是 **11 天**,靠人肉看日志才发现,不是靠监控。

实际代价:成交流攒了 1,099 万笔,但同期地面真值只进来 504 条。
「攒够 6-8 周就能开挖 edge」这个前提**其实一天都没成立过** —— 攒的是半截数据。

## A. 代码类

### A1. 给缺失值一个默认值 = 给它分配了极端优先级
*症状:队列/排序里某一类样本永远排在最前(或最后),而你没意识到*

```python
pending.sort(key=lambda r: r["end_date"] or "")   # None → "" → 最小 → 永远排队头
for r in pending[:80]:                             # 只处理前 80
```

`or ""` 看起来只是"防 None 崩溃",实际是**把所有缺失值钉死在优先级最高处**。
610 个 `end_date=None` 的市场因此霸占了全部 80 个名额 —— 而它们恰恰是**最不可能结算**的
(2027 年的盘)。37,700 个真正到期的市场,11 天一次没被查过。

→ **排序键里遇到缺失值,必须显式决定它排哪里,并写成判据。**
  正解:`(end_date is None, end_date or "")` —— 缺失值显式排尾。

### A2. 取 top-N 而不推进游标 = 任何一批坏样本都能永久堵死管线
*症状:计数恒定不变(如 `lookup_fail` 每轮都恰好是 2)*

即使 A1 修好,队头仍会被"到期但永不关闭"的市场长期霸占(实测队首 `end_date=2025-10-31`
但 `closed=False`,永远不会结算)。**只要每轮都从头取 top-N,队头卡死 = 整条管线卡死。**

→ **凡是"每轮处理前 N 个"的设计,必须问:第 N+1 个什么时候能轮到?**
  没有答案就是饿死。正解:游标轮转 + 回卷,并用判据焊死"连续跑满一圈必须覆盖全部"。

> 🔎 **恒定不变的计数是强烈的可疑信号。** 真实系统的计数会抖动;
> 一个数每轮都精确相同,通常意味着**每轮处理的是同一批东西**。

### A3. 阈值拍脑袋定 → 稳态被当成异常
*症状:告警每轮都推,久而久之没人看*

```python
rf = counts["register_fail"] + counts["settlement_lookup_fail"]
if rf > 3:   # 阈值 3 从何而来?没人知道
```

实测 1530 轮:`register_fail` 中位 **6**、p99 **22**、max 40。阈值 3 → **76% 的轮次必然触发**,
累计 1340 条推送。且两条**独立链路相加**判定,既制造噪音**又掩盖单边真异常**。

→ **任何阈值必须先量实测分布,把分位数写进判据断言,让"我没放水"可复核。**
  独立链路分开判定;分母会变的指标用**比率**而非绝对值(这次分母从 80 变 800)。

## B. 数据接口类(最危险)

### B1. ⭐第三方 API 的默认过滤器,本身就是一个与结果相关的筛选器
*症状:批量请求 N 个,返回 M 个,M < N,而你觉得"大概有些脏数据"*

```
请求 100 个 condition_ids  →  只返回 72 个
缺的 28 个,抽样 8 个:全部 closed=True 且已结算
```

Gamma 的 `condition_ids=` **默认只返回未关闭市场**。若照直觉用它做真值回填,
产出的真值库会**系统性缺失全部已结算样本** —— 而且一声不吭,数量看着还"差不多"。

这与 2026-07-15「自建已结算代理静默丢掉 80% 样本」是**同一种病**,区别在于:
**这次的筛选器不在自己代码里,藏在第三方 API 的默认参数中。**

→ **铁律:用任何批量/过滤类接口前,先做「请求数 vs 返回数」对账,
  并抽样核对「丢的是哪一类」。数量对不上就是红灯,不许用"大概是脏数据"糊过去。**
  正解:两遍取并集(默认 + `&closed=true`),实测覆盖 100/100、零重叠。

> 这条能救命的原因:**丢样本本身不致命,丢得与结果相关才致命。**
> 随机缺失 = 噪声(无害);系统性只缺已结算的 = 真值库结构性作废。

## C. 监控设计类

### C1. 监控只覆盖显式失败,对"产出为 0"是瞎的
*症状:故障期间告警很多,但没有一条指向真正的故障*

最讽刺的事实:真值断供的 11 天里,告警系统推了 **1340 条**,
**没有一条是关于真值断供的**。推的全是"注册失败 6 次"这种稳态噪音。

→ **每条关键产出都要有一条"连续 N 轮为 0 就报警"的守护**,
  且必须区分「有活没干成」(异常)与「没活可干」(正常)。
  本项目已落地:`alerts.TRUTH_SUPPLY_ZERO_CYCLES`。

### C2. 告警洪水与监控盲点是同一枚硬币
噪音不只是烦人 —— **它让真信号无处可显**。1340 条"注册失败 6 次"训练出的条件反射是
"这玩意儿老响,不用看",于是即便当时真报了真值断供,也会被一起忽略。

→ **降噪不是体验优化,是可靠性工作。** 判据里要同时焊死两头:
  「稳态必须完全静默」+「真异常必须推」。任何新守护都要自带**防洪判据**
  (这次:`test_does_not_flood_during_outage` 断言断供 3 个间隔恰好推 3 条,
  而非每轮 —— 否则 11 天会推 1584 条,直接复刻被修掉的病)。

## 落地检查清单(改代码时逐条过)

- [ ] 排序/优先级里的缺失值,显式决定了排哪里吗?
- [ ] "每轮取前 N 个"的设计,第 N+1 个什么时候轮到?写判据了吗?
- [ ] 有没有哪个计数**恒定不变**?(每轮精确相同 = 每轮处理同一批)
- [ ] 批量接口:请求数 == 返回数吗?不等时抽样核对**丢的是哪一类**了吗?
- [ ] 阈值有实测分布支撑吗?分位数写进判据断言了吗?
- [ ] 分母会变的指标,用的是比率还是绝对值?
- [ ] 新增的关键产出,有"连续为 0"守护吗?
- [ ] 新增的告警,有防洪判据吗?稳态静默 + 真异常必推,两头都焊死了吗?
