## 1. 需求

### 三问

**Q1 服务哪条需求?**

不变量:**`dt` 目录名必须等于该目录下每一笔成交的真实 UTC 成交日。**

它现在不成立。而 `dt` 是分区键,任何人写一句 `WHERE dt BETWEEN ...` 就会**静默拿到一个偏样本** ——
不报错、不缺列、数量看着还"差不多",只有结论是错的。
这正是本项目反复栽的那个跟头(见 CLAUDE.md「静默失败检查清单」)。

**Q2 不做会怎样?**

如实分两半答:

- **它现在没有在造成错误结论。** 实查:全项目消费端**没有一处按 `dt` 过滤**,
  都是 `dt=*` 通配读全湖(`wash_trading_detector.py:64`、`follow_the_leader.py:372`、
  `wallet_skill_v3.py:276`、`wallet_skill_v4_matched.py:160`、`backfill_market_times.py:332`)。
  ⇒ **既往结论没有被污染,不需要撤回任何东西。**
- **它是一个已经上膛的陷阱。** 34.4% 的行(1,018 万笔)放错了抽屉,最狠的一个目录
  装着横跨 15 个月的成交。将来任何人(**包括我**)顺手写一句按分区过滤,
  就会拿到一个与结果相关的偏样本 —— 而且**看不出来**。

⇒ 诚实结论:**这是基建,不直接赚钱**。做它的理由是消掉陷阱,顺带让 `dt` 真的能用来裁分区
(V4/V6 那些要反复重跑的脚本现在每次都全表扫 1.4 GB)。

**Q3 做完怎么验证?**

1. 全湖断言 `dt = strftime(to_timestamp(timestamp),'%Y-%m-%d')` 的比例 = **100.0000%**
2. 重排**无损**:重排前后**每个自然键的条数逐一相等**(⚠️ 是条数不是集合,见 §4.1)
3. 写入端:喂一个**跨日界**的批次,断言写出多个文件且每个文件的 dt 都对
4. 变异:把分组逻辑改回 `rows[0]`,上面第 3 条必须红

### ⛔ 明确不做什么

- **不去重。** 重排会把原本散在不同分区的重复行凑到一起,那是 compaction 的活。
  重排这一步笔数必须一分不差,**少一笔就停**。
- **不动 compaction 的算法。** 它按分区读写、不重算 dt,重排后自然就对了。
- **不动 `audit/` 分区。** 心跳按写入时刻分区,本来就是对的。
- **不删旧目录。** 换名后 `raw_before_repartition/` 留着,由用户确认后再删。

## 2. 事实底账(2026-08-27 实测,均为跑出来的)

### 2.1 错位的规模

| | |
|---|---|
| 全湖 | **29,615,569** 笔(自然键去重后 29,615,121,重复 448 笔 = 0.0015%) |
| `dt` 与真实成交日**一致** | 19,436,243 = **65.6%** |
| **错位** | **10,178,878 笔 = 34.4%** |
| 当前分区数 | **41** |
| 按真实成交日应有 | **460** |

错位幅度分布:

| 差多少 | 笔数 | 占比 |
|---|---|---|
| 1 天 | 3,088,111 | 10.43% |
| 2~7 天 | 1,549,862 | 5.23% |
| 8~30 天 | 1,768,492 | 5.97% |
| **31~180 天** | **3,500,222** | **11.82%** |
| >180 天 | 272,191 | 0.92% |

错得最狠的分区(目录名 → 里面真实成交日的跨度):

```
dt=2026-08-01    894,455 笔   2025-05-13 ~ 2026-08-01   ← 15 个月塞进一个抽屉
dt=2026-07-30    827,498 笔   2025-05-13 ~ 2026-07-30
dt=2026-07-26  1,146,179 笔   2025-05-14 ~ 2026-07-26
```

### 2.2 根因

`11-collector/storage_engine.py:64`:

```python
day = dt.datetime.fromtimestamp(int(rows[0]["timestamp"]), dt.UTC).strftime("%Y-%m-%d")
```

**整批按 `rows[0]` 的日期归档。** 巨盘回填一次抓回一年历史,全都记成"今天"。
差 1 天那 10.43% 是跨日界的正常轮询批次;差 1~6 个月那 11.82% 是回填。

### 2.3 修起来为什么比看着便宜(都已实查)

| 事实 | 出处 |
|---|---|
| `dt` **只是目录名**,不在 parquet 文件里 ⇒ 只有一个真值来源,不存在两份打架 | `TRADES_SCHEMA` 无 `dt` 字段;实读单个文件的 schema 确认 |
| 湖只有 **1.4 GB / 41 分区 / 746 文件**,磁盘剩 **540 G** | `du` / `df` |
| **没有任何代码按 dt 过滤** ⇒ 重排不改变任何现有结论 | 全项目 grep |
| `write_trades` 的**返回值没有被使用** ⇒ 改成写多文件不打破调用方 | `collector_core.py:330`、`backfill_closed_markets.py:228` |
| 市场水位线是 `SELECT max(timestamp) ... GROUP BY condition_id`,**从湖本身算出来** ⇒ 写一半崩了,水位线也只到一半,下轮自己接着补 | `storage_engine.all_watermarks` |

最后一条尤其要紧:它排除了我最担心的那个风险 ——
「写一半崩掉 ⇒ 水位线跳过没写的那段 ⇒ 永久缺口」。**这个机制在这里不成立。**

## 4. ⭐设计 review(2026-08-27,动代码之前)

> 触发:用户说「**我担心你修改又带来新的 bug,请针对修改内容进行 review**」——

### 4.1 🔴 我自己设计里的对账口径是错的

v1 写的是「**自然键集合**完全相同」。
而湖里有 **448 笔重复行**(同一自然键出现多次)⇒ 用**集合**比会把重复折叠掉,
**丢掉一笔重复也发现不了**。

⇒ **改为:比每个自然键的条数(multiset)。** 任何一个键的条数对不上就停。

### 4.2 🔴 新引入的静默劣化:碎片文件永远够不到 compaction 阈值

按天分组之后,一次写入会散成多个文件。

> ### ⚠️ 2026-08-27 当天更正:我把这条的量级说大了一个数量级
>
> 原文写「一次回填会写出 **300~400 个**碎片」。**错了**,而且错在**量错了对象**:
> 我量的是 `compacted-*` 文件的跨度(中位 295 天)—— 那代表**整个分区**的跨度,
> 不是**一次 `write_trades` 调用**的跨度。
>
> 实测未合并的 676 个原始文件(每个恰好代表一次写入调用):
> **一次写入横跨的成交日数 中位 1 天 / p90 4 天 / 最大 112 天;64.8% 就是单日**。
> ⇒ 改完之后这 676 次写入产生 **1,627 个文件,是 2.4 倍,不是 400 倍**。
>
> ⇒ 结论方向不变(薄页问题真实存在、compaction 阈值确实够不到),
> 但**紧迫度低一个数量级** ⇒ 支持「先只改写入端,整理工推到 V6 判决之后」这个决定。

而 `compact_due_partitions` 的触发条件是 **每个分区文件数 > `min_files`(=50)**。
这些碎片**摊在 400 个分区里,每个分区只有一两个文件 ⇒ 永远够不到 50,永远不会被合并**。

后果:读性能慢慢烂掉,而且**没有任何东西会报警** —— 典型的静默劣化,
而且是**这次改动新引入的**,v1 里完全没有。

⇒ 仍必须解决,但按更正后的量级,**可以推到 V6 判决之后**(用户 2026-08-27 拍板)。
方案见 §5.3,已进交接待办。

### 4.3 重排期间的写入竞态

停 timer 不够:

- systemd `Persistent=true` 会在**恢复 timer 时补跑**漏掉的那一轮
- 手工跑的 `backfill_closed_markets` 也会写
- 2026-08-26 已经发生过一次「停了 timer 忘了恢复」

⇒ 换名那一刻必须确认没有活着的写者;恢复 timer 必须写在 `try/finally` 里,
**不许挂在"后面某一步"上**。

### 4.4 内存

2,961 万行一次读进内存会爆。2026-08-18 的教训:**oomd 杀的是整个 cgroup**,
会把会话一起端掉。

⇒ 必须**逐源文件流式**处理,并用 `systemd-run --scope -p MemoryMax` 隔离。

### 4.5 重排后第一次 compaction 会让笔数**合法地**减少

原本散在不同分区的重复行被凑到一起,compaction 会折叠掉它们。
**这是正确行为**,但如果不提前写明:

- 若写个「笔数不许减少」的守卫 → 它会误报
- 若不预期 → 看到笔数掉了会以为重排丢了数据

⇒ 提前记在这里,并在重排完成时**出声报告**预计会被折叠的笔数。

### 5.1 治本 · 写入端

`write_trades(rows, day=None)`:

- `day` **显式传入时照旧**(判据 `test_compaction_sweep` 依赖它把文件塞进指定分区)
- `day is None` 时:按每行自己的 UTC 日期**分组**,每组写一个文件
- 返回值:改为 `list[Path]`(现有调用方都不使用返回值,已实查)

  打翻整批(同 §H2 既有做法)

### 5.2 治标 · 存量重排(只读 dry-run 先行)

```
① 停 collector timer(try/finally 保证恢复)
② 【只读】扫全湖,逐源文件统计:每个自然键的条数、每行应去的真实日期、
   预计新分区数、预计碎片文件数
③ 【只读】把上面的数字给用户看 ——⭐ 不写一个字节、不换名
④ 用户点头后:逐源文件流式读 → 按真实日期分组 → 写进新目录 raw_repartitioned/
⑤ 对账:总笔数逐字相等 + 每个自然键的条数逐一相等 + 每个新分区内 dt 一致率 100%
⑥ 对账过了才换名:raw → raw_before_repartition,raw_repartitioned → raw
⑦ 换完再验一次;旧目录**留着不删**,由用户确认后再删
⑧ 恢复 timer
```

### 5.3 解决 §4.2 的碎片问题

三个候选,**建议第 2 个**:

| 方案 | 做法 | 评价 |
|---|---|---|
| A | compaction 阈值改成全湖总文件数 | ⛔ 会把不该合的分区也合了,且阈值没有实测支撑 |
| **B(建议)** | **`compact_due_partitions` 增加一条触发:分区内存在"小于 N 字节的文件且文件数 ≥ 2"** | 直接对准"碎片"这个真实症状,不依赖数量阈值 |
| C | 写入端对跨多日的批次先在内存聚合再落盘 | 治标不治本;回填天然跨多日,聚合不掉 |

## 8. 代码 review(2026-08-27,`python-reviewer`)

判 **Block**。三条我都独立核实过,**全部属实**。

### 8.1 🔴 BLOCKER:`except` 漏了 `OverflowError` —— 承诺的保护是假的

`datetime.fromtimestamp` **在量级边界上换异常族**:

```
10**18  -> OSError        (接得住)      10**19 起 -> OverflowError   ← 接不住
-10**17 -> OSError        (接得住)      -10**20   -> OverflowError   ← 接不住
float('inf')              -> OverflowError                          ← 接不住
```

上游 `int(t.get("timestamp", 0))`(`collector_core.py:168`)**不限量级**,
Python 整数无上界 ⇒ 一个损坏但仍能被 JSON 解析成整数的值会原样穿过来,
让**整批**抛出去 —— 而 `poll_markets` / `backfill` 对 `write_trades` 都没有 try
⇒ **整轮采集被打死**,恰恰是本函数注释承诺"不许一颗老鼠屎打翻整批"要防的事。

⭐ **根源是我自己的实测方法有洞**:我探的是 `10**18` 和 `2**63-1`,
**两个恰好都落在 OSError 那一侧**,于是整个 OverflowError 族没被看见;
而判据的参数化又原样继承了同一个盲区,所以判据也没抓住。
形状同「只量了目标、没量非目标,就盖已验证章」。

⇒ 已修:`except (OSError, ValueError, TypeError, OverflowError)`,
并把 `10**19 / 10**20 / -10**20 / inf` 四个边界值补进参数化。

### 8.2 🔴 HIGH:`sorted()` 是正确性不变量,而我在注释里说它只是风格

我原写「排序只为落盘顺序稳定,便于人读与复现,**不影响正确性**」。**这是假话。**

机制:市场水位线 = 湖里该市场的 `max(timestamp)`,而轮询遇到 `ts <= wm` 就**停止翻页**
(`collector_core.py:169`)⇒ **比水位线旧的成交永远不会被再抓一次。**

- 按【旧→新】落盘:中途被杀 ⇒ 磁盘上是**时间前缀** ⇒ 水位线低报 ⇒ 下轮自愈 ✅
- 按【新→旧】(或用 dict 插入序 —— 那大致是 API 分页的新在前):中途被杀 ⇒
  新的几天已落盘、水位线抬到最新,**更旧、没写成的几天躺在它之下 ⇒ 永久缺口** 🔴

⇒ 已修:注释改写成硬不变量,并新增判据
`test_a_crash_midway_leaves_a_time_ordered_prefix_never_a_hole`
(monkeypatch `_write_one_partition` 在第 3 次调用时抛,断言
`max(已落盘) < min(未落盘)`)。变异「去掉 sorted」实测会红。

### 8.3 🔴 HIGH:丢弃行只 print,没有结构化读取者

同文件的 `compact_day` 早就是对的做法(收 `counts` 字典 → bump 具名字段 →
进 `AUDIT_FIELDS` → 心跳 → 日报兜底读取者)。只 print 到 stderr =
「记录事实 vs 使用事实,只接一头」,本项目已犯 5 次。

⇒ 已修:`write_trades` 加 `counts` 参数,新增心跳字段 `trade_day_unparsable_count`
(同时进 `COUNTER_KEYS` 与 `AUDIT_FIELDS`),由 `collector_core` 传入。
⛔ 刻意**不并进** `parse_reject_count` —— 那是"资产下标定位失败",成因与处置都不同。

⚠️ **回填路径刻意没接**:`backfill_closed_markets` 的 `write` 是可注入的测试接缝,
契约是 `write(rows)`,**12 处判据依赖它**。为让计数进心跳而把接缝改宽,
收益(回填的 counts 本来也不是心跳)小于代价。该路径的出声走 stderr → `backfill.log`。
**这是一个有意识的取舍,不是遗漏。**
