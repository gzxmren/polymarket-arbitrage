## 一、⭐⭐ 方向转变的依据:吃单和挂单是两笔完全不同的账

同一个盘口、同一时刻(2026-09-07 实测 `btc-updown-15m`):

| | 成本 | 手续费 | 结果 |
|---|---|---|---|
| **吃单 taker** | `ask+ask` = **1.0100** | **1.75%**(p=0.5 时) | 🔴 结构性必亏 |

`blockchainhansi/market_maker_polymarket` 的 README 把它讲得最清楚:

⇒ **纯套利(吃单)那条路结构性必亏,已可判死。真正的路是做市(挂单配对)。**

## 二、🔴 用户点名要把关的问题:**某个方向的流动性怎么处理**

调研下来这是**四层防御**,从最便宜(事前)到最贵(事后):

### 第 0 层 · 事前不进场 —— 最便宜,却最容易被忽略

来自 `poly-mm-core/docs/metrics.md`:

| 指标 | 判定 | 动作 |
|---|---|---|
| `vol_1s`(1 秒波动率) | < 0.02 价格稳 | ✅ 报价 |
| | > 0.10 价格在跑 | ❌ **跳过** |

原文理由:*"Dễ bị adverse selection - fill ở giá bất lợi khi giá đang trend"*
(**价格在趋势中时容易被逆向选择,会在不利价位成交**)。

⭐ **这条最重要**:方向性流动性问题的根源是**在不该报价的时候报了价**。
事后再怎么管库存,都不如一开始不进场。
配套还有价差守卫、深度守卫(见 `REFERENCE_IMPLEMENTATIONS` §4.2 那五条闸)。

### 第 1 层 · 报价偏斜 —— 连续调节,让市场帮你平仓

`blockchainhansi/src/config.py`:
```
skew = inventory × γ
库存偏 YES(inventory>0) ⇒ 压低 YES 的 bid、抬高 NO 的 bid
```
⇒ 不主动平仓,而是**改变报价让市场更愿意把你缺的那边卖给你**。

### 第 2 层 · 分级降险 —— 离散状态 + **迟滞**

`poly-mm-core/strategies/inventory_cap_mm.py`(648 行):

| 状态 | 触发 | 动作 |
|---|---|---|
| `NORMAL` | 风险 < soft_cap | 双边报价 |
| `DANGER` | soft_cap ≤ 风险 < hard_cap | 激进偏斜 + **减小单量** |
| `ONE_SIDED` | 风险 ≥ hard_cap | **撤掉所有会加仓的单,只报能减库存的那一边** |

- `soft_cap_pct = 0.6%` / `hard_cap_pct = 1.0%`(占账户权益)
- `one_sided_size_multiplier = 2.0`(加倍下单量,更快清)
- ⭐ **`exit_ratio = 0.7` 迟滞**:退出 ONE_SIDED 要等风险降到 `soft_cap × 0.7` 以下
  ⇒ **防止在阈值附近反复横跳**。这个细节很专业,值得抄。

### 第 3 层 · 主动兑现 —— ⭐ Polymarket 独有的工具

`poly-mm-core/run_merge.py` / `run_redeem.py`,`jherleth/pm-maker-bot` 也提到"链上 merge"。

**merge:1 YES + 1 NO → $1**(链上操作)。
⇒ 手里有 100 YES + 60 NO 时,可以 merge 掉 60 对**直接拿回 $60**,只剩 40 YES 裸头寸。
⇒ **这是把"配对成功的部分"立刻落袋、只留真实敞口的手段**,别的市场没有这个工具。
⚠️ 未验证:gas 成本、最小额度、到账延迟。**这是我们要自己测的。**

### 🔴 但四层的阈值**全部是拍的**

`0.02 / 0.10 / 0.6% / 1.0% / 0.7 / 2.0` —— **没有任何一个项目给出实测依据**。
⇒ 按本项目铁律(阈值必须有实测分布支撑),**结构可以抄,数字必须自己测**。

## 三、🔴 成交模型:整个回测可信度的命门

`poly-mm-core/core/orderbook.py`(769 行)的 `OrderbookSimulator`:

- **队列位置**:下单时记该档深度当 `queue_ahead`(**假设你永远排队尾**,保守)
- **队列前进**:深度减少,或该价位有成交 ⇒ `queue_ahead -= trade.size`
- **三种成交判定**:
  | 模型 | 何时算成交 |
  |---|---|
  | `conservative` | 队列排空**还有余**(queue < 0) |
  | `aggressive` | 队列一到 0 立刻成交 |
  | `hybrid` | 队列到 0 后按 `P(fill) = 1 − exp(−λt)`,**默认 λ=0.5** |
- ⭐ 细节:**撤单期间订单仍可能成交**(撤单有延迟,真实世界确实如此)
- ⭐ `_quote_cycle_fills = {cycle_id: {"bid": True, "ask": False}}` ——
  **它专门追踪"两边是否都成交"**,正是单腿风险的度量

### ⚠️⚠️ 三个未经验证的假设(这是最大的风险)

1. **λ = 0.5 没有任何校准依据** —— 代码里就是个默认参数。
2. **"我排队尾"是假设** —— 从公开 WS **只看得到每档总量,看不到队列内部**。
3. **"深度减少 = 我前进"是假设** —— 减少的可能是排在你后面的人撤单。

⇒ **整个回测的成交率完全由这三个假设决定,而它们都观测不到。**
⭐⭐ **这正是我们做影子盘的价值所在,而且目标现在很具体:
用真金白银的小额挂单实测「挂上去多久成交、成交率多少」,反过来校准 λ,
或者证明这个队列模型根本不成立。** 这是本项目能做而那八个项目都没做的事。

## 四点五、⭐⭐ 用 50 天历史盘口实测:吃单套利已死,做市有 2% 毛利空间

**数据来源**:`milanzandbak/backtesting15mbitcoin` —— **2025-10-30 ~ 12-20 共 50 天**、
**4,872 个 BTC 15m 窗口**的买价/卖价日志(约 900 行/窗口,毫秒级)。
⚠️ **先验解析再用**:抽一个文件逐行核对,924 行零失败、首行与肉眼一致才跑全量。
⚠️ **负价格出声计数**:378 万行中 **20,817 行(0.550%)** 含负价,已剔除并记账,非静默丢弃。

### 结果(各约 379 万行)

| | 中位 | p5 | p95 |
|---|---|---|---|
| **吃单成本 `ask+ask`** | **102 分** | 101 | 105 |
| **挂单口径 `bid+bid`** | **98 分** | 95 | 99 |

### 🔴 结论一:路 0(吃单纯套利)**可以判死了**

- `ask+ask < 100` 的时刻:**仅 0.84%**
- 扣 taker 手续费后(需 `< 98.25`):**仅 0.26%**

⇒ 而这 0.26% 还**没有**扣掉:抢不抢得到(机会短命、机器人先到)、深度够不够、两腿是否都成交。
**⇒ 有 378 万行数据支撑,纯套利(吃单)这条路关闭。**
⭐ 这正好补上了我 2026-09-07 三次采样脚本失败没测出来的那个问题。

### 🟢 结论二:做市侧 **95.57% 的时刻有毛利空间,中位 2%**

`bid+bid` 中位 98 分 ⇒ **两边都挂 bid 且都成交,毛利中位 2 分 = 2%**。
⚠️ **这是毛利,不是净利** —— 未扣单腿风险、逆向选择、以及"挂上去到底成不成交"。

### ⭐ 结论三:价差在窗口内**三个阶段完全一样**

| 阶段 | `ask+ask` 中位 | `bid+bid` 中位 |
|---|---|---|
| 0–5 分 | 102 | 98 |
| 5–10 分 | 102 | 98 |
| 10–15 分 | 102 | 98 |

⇒ 与直觉相反:**临近结算价差并没有变化**。若要择时,理由不能是"某个阶段价差更宽"。

### ⚠️ 结论四:价差可能正在收窄 —— **但这条只是推的,别当实测**

| | `ask+ask` | `bid+bid` | 做市毛利 |
|---|---|---|---|
| 2025-10~12(本数据,**无做市补贴**) | 102 | 98 | **2%** |
| 2026-09-07(我今天实测,**有 $225k 补贴**) | 101 | 99 | **1%** |

⇒ 若这个关系成立,**补贴带来竞争 ⇒ 价差收窄 ⇒ 做市反而更难赚**,
那么 **补贴退坡对做市是利好而非利空** —— 与 spec §2.5 现在写的判断相反。
🔴 **但这是两个时点的对比,期间还隔着 TWAP 改制等多个变化,属于「推的」。**
⛔ 在用同口径实测之前,不许把它当结论,更不许据此改 spec 的红线。

### 🔴 这份数据的时代边界(不许越界使用)

1. **2025 年数据,在 2026-08-07 TWAP 改制之前** ⇒ 那时结算是**单点快照价**
   ⇒ **任何与结算结果相关的分析都不能用**(胜率、校准、方向性策略回测全部作废)
2. **那时没有做市补贴**($1M 计划是 2026-08)
3. **只有最优买卖价,没有深度、没有成交记录** ⇒ **做不了队列模型回测**,
   只能做"价差空间有多大"这类结构性分析
⇒ ✅ 可用于:两腿和分布、价差结构、毛利空间
⇒ ❌ 不可用于:胜率、校准、成交概率、任何依赖结算机制的结论

## 四点六、🔬 实测「Chainlink 滞后 4–12 秒」——**真有滞后,但只有 3 秒**

**被验证的声称**(`0xLanister/polymarket-5-15min-printer-bot` README 原文):
> sees where Bitcoin is going ~**5–8 seconds before** the price updates on the platform
> Chainlink aggregates data from multiple exchanges → small delay due to
> **averaging + on-chain confirmation**. Typical delay: **4–12 seconds**.

⚠️ **它给的理由有一半不成立**:Polymarket 用的是 **Chainlink Data Streams**(链下低延迟推送,
`resolutionSource` 已查实),**不是链上 oracle** ⇒ "on-chain confirmation" 这部分不适用。
而且 README **没有任何测量数据**,4–12 秒是声称。

### ⭐ 测法:必须分离两种滞后

- **平均造成的滞后**:60 秒 TWAP 天然落后于瞬时价 —— 这是**数学性质,不是 edge**
- **真实传输滞后**:才是可能的 edge

⛔ 直接拿币安现货比 Chainlink TWAP,会把前者误当成后者。
✅ 正确做法:**用币安逐笔自己算一个 60 秒 TWAP**,与 Chainlink 60 秒 TWAP 比 ——
同口径,平均效应被约掉,剩下的才是真实滞后。再做**互相关**找峰值。

### 结果(2026-09-07,采样 360 秒)

币安逐笔 **10,130 笔** / Chainlink TWAP **411 点** / 两路同口径重叠 **296 秒**

| 平移 k | 相关系数 r |
|---|---|
| 0 s | +0.996921 |
| 2 s | +0.998792 |
| **3 s** | **+0.999128** ← 峰值 |
| 4 s | +0.999085 |
| 8 s | +0.995061 |
| 12 s | +0.985051 |
| 20 s | +0.947820 |

⭐ **实测滞后 = 3 秒**(声称是 4–12 秒)⇒ **方向对(确实滞后),但数值被夸大了。**
同刻基差 −15.33 USD = **−1.92 bp**(与 09-07 早先测的 1.45 bp 同量级)。

### ⚠️ 这个测量的边界(别外推)

1. **单次、296 秒、一个时段**;k=2/3/4 的 r 都 >0.9987 ⇒ 分辨率有限,真值可能在 **2–4 秒**之间
2. 我用"逐笔→每秒最后价→60 秒简单平均"算币安 TWAP,而 **Chainlink 聚合多家交易所、加权方式未公开**
   ⇒ 算法差异会污染测量
3. 没有覆盖**高波动时段**(声称说延迟随波动上升)

### 🔴🔴 但最关键的一点:**滞后存在 ≠ 能赚钱**

我测的是 `Chainlink TWAP 滞后币安 3 秒`。要赚钱需要的却是另一件事:
> **Polymarket 的市场报价** 滞后于 **可从币安推算出的结算值**

这两者不同 —— 因为**做市商也看得到币安**。若他们比我们快(几乎确定),
他们的报价早已把这 3 秒反映进去了,**我们看到的盘口不是"还没反应"的盘口**。

⇒ **下一个该测的是:Polymarket 盘口对币安价格变动的反应延迟**(而不是 Chainlink 的)。
这才是 spec §3.2「路 A · 执行速度」真正要量的东西。
⚠️ 而它要与我们自己的**热连接往返延迟**比 —— 那个数至今**只测过冷连接(0.65~4.8 秒)**,仍欠着。
