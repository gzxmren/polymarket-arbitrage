## 一、⭐⭐ 方向转变的依据:吃单和挂单是两笔完全不同的账

同一个盘口、同一时刻(2026-09-07 实测 `btc-updown-15m`):

| | 成本 | 手续费 | 结果 |
|---|---|---|---|
| **吃单 taker** | `ask+ask` = **1.0100** | **1.75%**(p=0.5 时) | 🔴 结构性必亏 |
| **挂单 maker** | `bid+bid` = **0.9900** | **零 + 20% 返佣** | 🟢 毛利 **1%** |

`blockchainhansi/market_maker_polymarket` 的 README 把它讲得最清楚:
> 买 10 YES @ **$0.48** + 10 NO @ **$0.48** ⇒ 成本 $9.60,**保证赔付 $10.00**,利润 $0.40(4.2%)

⇒ **纯套利(吃单)那条路结构性必亏,已可判死。真正的路是做市(挂单配对)。**
⚠️ 代价:做市**会亏钱**(单腿风险 + 逆向选择),不再符合用户原话「不会造成损失」。
**用户 2026-09-07 知情并拍板转向。**

## 二、🔴 用户点名要把关的问题:**某个方向的流动性怎么处理**

调研下来这是**四层防御**,从最便宜(事前)到最贵(事后):

### 第 0 层 · 事前不进场 —— 最便宜,却最容易被忽略

来自 `poly-mm-core/docs/metrics.md`:

| 指标 | 判定 | 动作 |
|---|---|---|
| `vol_1s`(1 秒波动率) | < 0.02 价格稳 | ✅ 报价 |
| | > 0.10 价格在跑 | ❌ **跳过** |

原文理由:*"Dễ bị adverse selection - fill ở giá bất lợi khi giá đang trend"*
(**价格在趋势中时容易被逆向选择,会在不利价位成交**)。

⭐ **这条最重要**:方向性流动性问题的根源是**在不该报价的时候报了价**。
事后再怎么管库存,都不如一开始不进场。
配套还有价差守卫、深度守卫(见 `REFERENCE_IMPLEMENTATIONS` §4.2 那五条闸)。

### 第 1 层 · 报价偏斜 —— 连续调节,让市场帮你平仓

`blockchainhansi/src/config.py`:
```
skew = inventory × γ
库存偏 YES(inventory>0) ⇒ 压低 YES 的 bid、抬高 NO 的 bid
```
⇒ 不主动平仓,而是**改变报价让市场更愿意把你缺的那边卖给你**。

### 第 2 层 · 分级降险 —— 离散状态 + **迟滞**

`poly-mm-core/strategies/inventory_cap_mm.py`(648 行):

| 状态 | 触发 | 动作 |
|---|---|---|
| `NORMAL` | 风险 < soft_cap | 双边报价 |
| `DANGER` | soft_cap ≤ 风险 < hard_cap | 激进偏斜 + **减小单量** |
| `ONE_SIDED` | 风险 ≥ hard_cap | **撤掉所有会加仓的单,只报能减库存的那一边** |

- `soft_cap_pct = 0.6%` / `hard_cap_pct = 1.0%`(占账户权益)
- `one_sided_size_multiplier = 2.0`(加倍下单量,更快清)
- ⭐ **`exit_ratio = 0.7` 迟滞**:退出 ONE_SIDED 要等风险降到 `soft_cap × 0.7` 以下
  ⇒ **防止在阈值附近反复横跳**。这个细节很专业,值得抄。

### 第 3 层 · 主动兑现 —— ⭐ Polymarket 独有的工具

`poly-mm-core/run_merge.py` / `run_redeem.py`,`jherleth/pm-maker-bot` 也提到"链上 merge"。

**merge:1 YES + 1 NO → $1**(链上操作)。
⇒ 手里有 100 YES + 60 NO 时,可以 merge 掉 60 对**直接拿回 $60**,只剩 40 YES 裸头寸。
⇒ **这是把"配对成功的部分"立刻落袋、只留真实敞口的手段**,别的市场没有这个工具。
⚠️ 未验证:gas 成本、最小额度、到账延迟。**这是我们要自己测的。**

### 🔴 但四层的阈值**全部是拍的**

`0.02 / 0.10 / 0.6% / 1.0% / 0.7 / 2.0` —— **没有任何一个项目给出实测依据**。
⇒ 按本项目铁律(阈值必须有实测分布支撑),**结构可以抄,数字必须自己测**。

## 三、🔴 成交模型:整个回测可信度的命门

`poly-mm-core/core/orderbook.py`(769 行)的 `OrderbookSimulator`:

- **队列位置**:下单时记该档深度当 `queue_ahead`(**假设你永远排队尾**,保守)
- **队列前进**:深度减少,或该价位有成交 ⇒ `queue_ahead -= trade.size`
- **三种成交判定**:
  | 模型 | 何时算成交 |
  |---|---|
  | `conservative` | 队列排空**还有余**(queue < 0) |
  | `aggressive` | 队列一到 0 立刻成交 |
  | `hybrid` | 队列到 0 后按 `P(fill) = 1 − exp(−λt)`,**默认 λ=0.5** |
- ⭐ 细节:**撤单期间订单仍可能成交**(撤单有延迟,真实世界确实如此)
- ⭐ `_quote_cycle_fills = {cycle_id: {"bid": True, "ask": False}}` ——
  **它专门追踪"两边是否都成交"**,正是单腿风险的度量

### ⚠️⚠️ 三个未经验证的假设(这是最大的风险)

1. **λ = 0.5 没有任何校准依据** —— 代码里就是个默认参数。
2. **"我排队尾"是假设** —— 从公开 WS **只看得到每档总量,看不到队列内部**。
3. **"深度减少 = 我前进"是假设** —— 减少的可能是排在你后面的人撤单。

⇒ **整个回测的成交率完全由这三个假设决定,而它们都观测不到。**
⭐⭐ **这正是我们做影子盘的价值所在,而且目标现在很具体:
用真金白银的小额挂单实测「挂上去多久成交、成交率多少」,反过来校准 λ,
或者证明这个队列模型根本不成立。** 这是本项目能做而那八个项目都没做的事。
