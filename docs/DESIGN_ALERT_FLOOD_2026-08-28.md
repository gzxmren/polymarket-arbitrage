# 告警防洪:让持续故障不再把队列冲垮

**日期**:2026-08-28   **作者**:Claude(与用户对话中定题)
**流程**:六步流程第 1~3 步(需求 / 设计 / 设计 review)。第 4 步起另见提交。
**判定**:这是**改告警口径**,不是已定位的 bug 修复 ⇒ 走完整六步(已当场向用户出声)。

## 一、需求

### 1.1 三问

**Q1. 服务哪条需求?**

CLAUDE.md 静默失败清单第 7 条:

> 新增告警必须自带防洪判据:**稳态完全静默 + 真异常必推,两头都要焊死**。
> 降噪不是体验优化,是可靠性工作 —— 噪音会让真信号无处可显。

现状:**只焊了一头**。

| | 实测 | 状态 |
|---|---|---|
| 稳态完全静默 | 08-15 / 08-16 / 08-24 / 08-25 四个健康日,两条告警各 **0** 次 | ✅ 已成立 |
| 持续故障不许洪水 | 08-19 单日**推送尝试 69 轮**;08-20 59;08-21 52;08-18 35 | ❌ 没焊 |

**Q2. 不做会怎样?——「噪音淹没真信号」在本项目已经不是比喻,是实测发生过的事**

待发队列 `alerts.PENDING_MAX = 20`,满了**丢最老的**。
2026-08-14 实测:通道中断 **458 分钟**,期间告警每轮都来 ⇒ 恢复时那条消息写着

> ✅ 已推送告警 20 条,其中**补发 20 条**(推送通道曾中断约 458 分钟);
> **另有 41 条因队列上限被丢弃**

⭐ **关键机制(这是本设计的立论点)**:洪水本身不丢告警 —— 08-19 推了 69 轮,一条没丢,
因为通道是通的。**真正致命的是「洪水 + 通道中断」同时发生**,而这两件事**同源**:
把采集器打成退化的那个网络故障,同时也会打断 Telegram。⇒ 它们**必然共同出现**,
不是两个独立小概率事件相乘。08-14 就是这么丢的 41 条。

不做的后果:下一次网络退化(实测近三周发生过 3 次)会重演 08-14 —— 而这次队列里
可能装着的是 `🔴 增量 offset 截断`(唯一被证明与**永久数据丢失**挂钩的那条,
本次核查刚确认它 6 次全部真发出去过,其中 08-14 那次正是靠"够新"才没被挤掉)。

**Q3. 做完怎么验证?**(判据先写,见 §4)

- **稳态**:用 08-24 / 08-25 **真实心跳**重放 ⇒ 消息数必须 **0**
- **持续故障**:用 08-19 **真实心跳**重放 ⇒ 消息数从 **69** 降到 **≤ 8**
- **真异常必推**:故障发生的**第一轮**必须推(不许"攒够 N 轮才说")
- **不许静默吞掉**:被折叠的次数必须出现在下一条消息里(出声计数,项目铁律)

### 1.2 明确**不做**什么

1. ⛔ **不修看门狗的「间歇盲区」** —— 今天已实测判为不重要:退化四天的永久损失是
   4 条截断留痕,而**全部**属于同一个刷单盘(已在排除名单里),非刷单盘永久损失 **0**。
2. ⛔ **不改 `PENDING_MAX`** —— 调大只是把溢出推迟,且"丢最老留最新"的策略方向是对的
   (告警是状态描述,新的更能反映现状)。治洪水不是治堤坝。
3. ⛔ **不改任何告警的正文措辞** —— 正文有判据在验,动它会连带一批判据。
4. ⛔ **不动 `🔴 增量 offset 截断`(warm)那条的触发条件** —— 实测它稳态静默、
   真异常 6/6 全推出去了,是唯一被证明有效的那条。只让它**参与**节流层(见 §2.4)。
5. ⛔ **不删除已有的 5 处 `% N == 0` 守卫** —— 理由见 §2.5 被否备选 C。

## 二、设计

### 2.1 现状盘点:8 个触发,防洪覆盖不全

`alerts.build_alert()` 共 8 类触发。逐条量:

| # | 触发 | 现有防洪 | 对**持续**故障 | 对**间歇**故障 |
|---|---|---|---|---|
| 1 | 成交流持续断供 | `tfs % 6 == 0` | ✅ | ❌ streak 归零 |
| 2 | **firehose 抽风(else 分支)** | **无** | ❌ 每轮推 | ❌ 每轮推 |
| 3 | 成交流已恢复 | 只推一次 | ✅ | ✅ |
| 4 | offset 截断尖峰 | 阈值 ≥20 | ❌ 持续时每轮推 | ❌ |
| 5 | 增量 offset 截断(warm) | 无(设计如此) | 稳态静默,可接受 | 同左 |
| 6 | 注册链路断供 | `rzs % 18 == 0` | ✅ | ❌ streak 归零 |
| 7 | **结算守望查询失败** | **无** | ❌ 每轮推 | ❌ 每轮推 |
| 8 | 结算真值断供 | `zs % 18 == 0` | ✅ | ❌ streak 归零 |
| 9 | 轮转游标空洞 | `rhs % 3 == 0` | ✅ | ❌ streak 归零 |
| 10 | 慢周期 | `scs % 4 == 0` | ✅ | ❌ streak 归零 |

⭐ **两个发现**:

**(a) 用户点名的第 7 条不是唯一的洞,第 2 条同样裸奔**,而且更隐蔽 ——
它是 `if tfs >= 6: ... else: <每轮推>` 的 else 分支,读代码时看着"有节流"。
实测 08-19 该分支触发 **43 轮**。

**(b) ⭐⭐ 连计取模这一整族对「间歇故障」全部失效。**
08-18~21 那次退化是**约 50% 占空比的间歇**(这也正是看门狗当时没报的原因):
streak 涨到 2、3 就被一轮成功清零,`% N == 0` 永远够不到。
⇒ **不能靠再加一个 `% N == 0` 解决问题**,那正是第 6 遍抄同一个不管用的结构。

### 2.2 选定方案:按触发类型的时间冷却,**拆成三层,有状态的只有最外一层**

> ⭐ 本节在 §3 的 R1 / R2 之后**已修订**。原稿把冷却写在 `build_alert` 内部,
> 会把它从纯函数变成有副作用的函数,打断 18+ 条现有判据 —— 详见 R1。

```
build_alert_keyed(counts)          → [(key, text)]      纯函数(新增)
throttle(pairs, state, now)        → (放行, 新state, 欠report) 纯函数,状态从参数进出(新增)
build_alert(counts)                → str | None          纯函数,**签名与行为逐字不变**
maybe_alert_with_counts(counts)    → 唯一读写状态文件的地方(已存在,只在此接线)
```

- `build_alert` 保持 `"\n".join(t for _, t in build_alert_keyed(counts))` ⇒ 现有判据一律继续有效
- 冷却逻辑用**纯函数判据**验:state 和 now 都是入参,不需要假时钟、不需要碰文件
- 状态文件按链路分:`_throttle_path(link)`,与 `_queue_path(link)` 同形(R3)

**放行规则**:

1. 某 key 本轮触发且**不在冷却窗内** → 放行,记下时刻
2. 某 key 本轮触发且**在冷却窗内** → 压住,`suppressed[key] += 1`
3. ⭐ 本轮**只要有任何一条**放行,就把**所有** key 欠着的 `suppressed` 作为尾巴附在消息后
   (「另:结算守望查询失败在过去 3.0 小时内又发生 5 次,未单独推送」),然后清零 —— 这条是 R2 的修复,
   保证被压住的次数**不会随故障消失而蒸发**
4. 故障消失、且始终没有下一条消息时,`suppressed` **留在 state 里不清零**,等下一条消息带走

**为什么冷却而不是连计**:冷却按**墙上时钟**算,间歇故障照样被压住;
连计按**连续轮数**算,一轮成功就归零。实测依据见 §2.1(b)。

### 2.3 ⭐ 关键设计:key 在**产生处**给,不从正文反推

本项目已有一处冷却(`collector_watchdog._cooldown_signature`),它的签名是
**把正文里的数字抹掉**得到的。这个办法**已经坏过两次**:

- 2026-08-19:正则 `\d+` 抹不掉「20 条」变「7 条」以外的形态 ⇒ 冷却完全失效,
  触发 136 次推出去 63 次
- 2026-08-26:同一处**复发** —— `\d+` 抹不掉**千分位逗号**,
  「12,246 个」→`#,#` 而「907 个」→`#`,签名照样每轮不同

两次同一个根因:**签名依赖正文的偶然形态**。任何人改一句文案就可能再次冲垮它。

⇒ 本设计**结构性地消除这个失败模式**:把

```python
triggers.append(f"⚠️ 结算守望查询失败 {sf}/{sc}(…)")
```

改成

```python
triggers.append(("settlement_lookup_fail", f"⚠️ 结算守望查询失败 {sf}/{sc}(…)"))
```

key 是**写死的字面量**,与正文里有几个数字、有没有逗号**完全无关**。
共 10 个 append 点,一次改完。

### 2.4 冷却窗取值:**12 轮 = 180 分钟(3 小时)**

> ⭐ 本节在 §3 的 R4 之后**已修订**。原稿用 `458/冷却×8 ≤ 20` 倒推出"≥183 分钟",
> 那个不等式假设 8 类触发全活且全错开 —— 实测 08-19 最多同时活 2 类。
> 拿一个不会发生的世界定参数,正是「判据的工况参数必须来自现网实测」在骂的事,已降级。

**取值理由**:落在本项目既有档位家族里(轮转 3 轮 / 慢周期 4 轮 / 成交流 6 轮 / 真值 18 轮),
且 12 能被 3、4、6 整除 —— 这一点在 R5 里被验算证明**能避免与现有 `% N == 0` 叠加造成饿死**,
不是凑数。

**红线不建在取值上,建在重放实测上**(§3 R7):
稳态(08-24/25)必须 0 条;持续故障(08-19 / 08-20)必须从 68 / 59 降到 ≤ 8。
`458/冷却×8 ≤ 20` 保留为**粗略合理性检查**:180 分钟 ⇒ 最坏 24 条,略超队列 20 格,
而实测工况(≤2 类同时活)下是 6 条。**这个放宽是有意的,写在这里以便被打。**

### 2.5 被否掉的备选

**A. 给第 2、7 条各加一个 `% N == 0`(照抄现有 5 处)**
→ 否。①对间歇故障无效(§2.1b 实测);②这是 CLAUDE.md 点名的「照抄结构而不抽象」
第 6 遍(时间闸抄 5 遍、连零守护抄 4 遍已在案)。

**B. 复用看门狗那套「抹数字得签名」的冷却**
→ 否。同一实现已坏两次(§2.3),且第二次是**复发**。复用它等于把一个已知会
周期性失效的机制扩散到第二处。

**C. 顺手把已有 5 处 `% N == 0` 删掉,统一走新节流层**
→ 否。**一次只动一个自变量**。删掉它们需要对每条告警逐一回归证明,
成本远大于收益;留着只会让那几条更安静,不会更吵。
列为**已知冗余**(见 §3 边界),后续可选清理。

**D. 全局令牌桶(每 N 轮最多一条消息,不分类型)**
→ 否。会把一个**新出现的、不同类型的**真故障一起压住 —— 那正是要保护的东西。

### 2.6 要用户拍板的点

1. **冷却窗 3 小时**是否可接受?后果:持续故障期间,同一类问题每 3 小时提醒一次
   (08-19 那种烈度下,一天从 69 条降到约 8 条)。想更吵就调小,但队列余量会变薄。
2. **是否同意本次不碰看门狗的间歇盲区**(§1.2 第 1 条,今天已实测判为不重要)。

### 2.7 已知边界(说清楚这个设计**不能**解决什么)

- **管不了看门狗自己的告警。** 看门狗是另一个进程、另一条链路(`link="watchdog"`),
  有它自己的队列和那套抹数字的冷却。本次不动它 ⇒ 它仍可能自己刷屏。
- **管不了「通道断了喊不出来」。** 网络坏时告警走同一条坏网络,这条至今未做
  (见 [[pitfall-watchdog-blind-to-empty-cycles]]),本设计只减少要喊的条数。
- **不保证一条都不丢。** 若通道中断远超 458 分钟(比如一整天),队列仍会溢出 ——
  只是把"41 条"降到个位数,且**丢弃数仍会出声**。
- ~~**冷却状态丢失(文件损坏/被删)会退化成"立刻推一条"**,不是静默。方向是安全的。~~
  🔴 **2026-08-28 code review 实测:这句话原先是假的**,已修(见 §五 R1)。
  它只对"读不出来"成立;**"语法合法但形状不对"会直接崩**,而崩的后果远比静默严重。
  加了 `isinstance` 防护 + 6 条坏输入判据之后,这句话才成立。

## 三、设计 review(2026-08-28,动代码**之前**做)

**谁审的**:我自己,对着上面这份还没写一行代码的设计逐条找失败场景。
**结论**:**发现 2 个 BLOCKER + 3 个须改 + 2 个可接受风险**。§二 已按此修订(见每条的「改动」)。

### R1 🔴 BLOCKER — 把冷却塞进 `build_alert` 会打断 18+ 条现有判据

**这是我自己设计里的错。** §2.2 那张流程图画的是"在 `build_alert` 之上加一层",
但 §2.3 的改法(在 `triggers.append` 处给 key)是**写在 `build_alert` 内部**的 ——
一旦冷却状态也在里面读写,`build_alert` 就从**纯函数**变成了有副作用的函数。

实测现有判据把它当纯函数用,而且**在循环里反复调**:

| 文件 | 调用次数 |
|---|---|
| `test_trade_flow_outage_guard.py` | **12** |
| `test_rotation.py` | 3 |
| `test_alert_queue.py` | 2 |
| `test_history_truncation.py` | 1 |
| `test_register_supply_guard.py` / `test_alerts_fail_thresholds.py` | 多处 `maybe_alert` |

典型形状 `for streak in ...: assert alerts.build_alert({...}) is None` ——
第二次调用起就会撞上自己上一次留下的冷却,断言全部失去意义。
⚠️ 更糟的是它们**多半会变绿而不是变红**(冷却让返回 `None` 更容易),
即"判据还在,但已经不验证任何东西"—— 正是 [[lesson-tests-that-dont-run-production-path]] 那个形状。

**改动(已写回 §2.2)**:拆成三层,**有状态的那层单独拿出来**:

```
build_alert(counts)          → str | None     纯函数,签名与行为**逐字不变**(现有判据全部继续有效)
build_alert_keyed(counts)    → [(key, text)]  纯函数,新增
throttle(pairs, state, now)  → (放行的 pairs, 新 state, 被压计数)   纯函数,状态**从参数进出**
```

`build_alert` 改为 `"\n".join(t for _, t in build_alert_keyed(counts))`,
读写状态文件只发生在 `maybe_alert_with_counts` 那一层。
⇒ 冷却逻辑可以用**纯函数判据**验,不用碰文件、不用假时钟猴补。

### R2 🔴 BLOCKER — 被压住的次数可能永远没人知道(静默丢弃)

§1.1 Q3 写了"被折叠的次数必须出现在**下一条消息**里",但设计里没说**哪一条**。
失败场景很具体:

> 结算查询失败在 10:00 推一条,10:15~11:30 又触发 5 次被压住,11:45 故障自己好了。
> 此后再没有这个 key 的消息 ⇒ **那 5 次永远不会被报告**。

这违反项目铁律「任何降级/剔除/回退,必须出声计数」,而且是**告警系统自己在静默丢弃**。

**改动(已写回 §2.2)**:被压计数存在 state 里,**挂在下一条外发消息上,不论那条是哪个 key**;
且故障消失时(该 key 本轮不再触发)必须把欠着的计数结清 —— 结清本身**不算新告警**,
只作为尾巴附在下一条消息后面。若直到进程重启都没有下一条消息,计数随 state 保留,不清零。

### R3 🟡 须改 — 冷却状态必须按 link 分文件

`alerts.py` 里 `_queue_path` 上方已经写着这个教训:
「采集器与看门狗会**同时**跑,共用一个文件会在读-改-写之间丢条目 —— 而丢的正是告警本身」。

本次核查:`build_alert` 目前**只有采集器一条链路**在调(回填走 `build_backfill_alert` +
`link="backfill"`),所以今天不会出事。但**明天有人给回填也加上就会**,
而那时症状是"冷却偶尔失效",极难归因。

**改动**:状态文件走 `_throttle_path(link)`,与 `_queue_path(link)` 同形。零成本,先焊死。

### R4 🟡 须改 — §2.4 那个不等式是装饰,判据不该建在它上面

我写了 `458 / 冷却 × 8 ≤ 20 ⇒ 冷却 ≥ 183 分钟`,然后取了 180 并解释"差 3 分钟可接受"。
**这个讨论本身就是错的重点**:它假设 8 类触发全活且全错开,而实测 08-19 最多同时活 2 类;
拿一个不会发生的世界去定参数,正是「判据的工况参数必须来自现网实测」那一条在骂的事。

**改动**:冷却窗取 **12 轮(3 小时)**,理由改为"落在本项目既有档位家族(3/4/6/18 轮)";
那个不等式降级为**粗略合理性检查**,不作为红线。
真红线用**重放实测**(见 R7),那是现网真实工况。

### R5 🟡 须改 — 与现有 5 处 `% N == 0` 叠加,要证明不会"永久压住"

两层节流叠加时,若某个 key 的触发时刻**恒好落在冷却窗内**,它就永远发不出来 ——
一个由防洪机制自己制造的静默失败。**已逐条验算**(冷却 = 12 轮):

| 触发 | 模 | 首推 | 冷却后下一个能推的时刻 | 会不会饿死 |
|---|---|---|---|---|
| 轮转游标空洞 | %3 | 3 | 15(15%3=0 ✓) | 否 |
| 慢周期 | %4 | 4 | 16(16%4=0 ✓) | 否 |
| 成交流断供 | %6 | 6 | 18(18%6=0 ✓) | 否 |
| 注册/真值断供 | %18 | 18 | 30 → 实际 36(36%18=0 ✓) | 否 |

12 能被 3/4/6 整除是这里的关键。**改动**:把这张表写进判据注释,
并加一条判据"任一 key 在持续故障下 24 小时内至少推 2 次"(防饿死那一头)。
⚠️ 若日后有人改冷却窗为 5 或 7 轮,%3/%4/%6 就不再对齐 ⇒ 判据必须能抓到,故按上表逐行断言。

### R6 🟢 可接受 — 同 key 内的"升级"会被压住

`settlement_lookup_fail` 在 51% 和 100% 是同一个 key,后者会被前者的冷却压住。

## 四、实施记录(第 4 步 TDD)

### 4.1 与 §二设计的三处偏离(写下来是为了能被打)

**① `maybe_alert` 有意**不**节流 —— 设计里漏了它是转调关系**

设计说"接线点是 `maybe_alert_with_counts`",但没注意到 `maybe_alert` 的实现就是
`return bool(maybe_alert_with_counts(counts)["sent_fresh"])` ⇒ 节流会被它继承,
而约 15 条老判据在循环里调它并断言 True/False,会**一起变行为**。

改法:`maybe_alert` 直接走 `build_alert + dispatch`,不经节流,并在 docstring 写明这是有意的。
- 为什么可以这样:生产路径不走它(`test_alert_queue.py` 有判据焊死 run_cycle 不许用 `maybe_alert(`)
- 为什么不算"两套实现分叉":它与生产路径共用 `build_alert` + `dispatch`,少的只是节流那一层,
  没有复制任何逻辑。⚠️ 但这是**需要盯着的地方** —— 已把这个判断交给 code review 复核。

**② `build_alert` 不是简单 join ⇒ 多拆一个 `compose_body`**

原正文 = 标题壳 + 触发行 + 本轮摘要。节流之后"要发的行"不再等于"本轮触发的行"
(会少几行、又多一行"被压住 N 次"的尾巴),而壳必须逐字不变(既有判据验的是壳)。
故拆出纯函数 `compose_body(lines, counts)`。

**③ ⭐ 红线的单位换了:从「全天 ≤8 条」换成「458 分钟窗内 < PENDING_MAX」**

判据第一版写的是"退化日全天消息数 68 → ≤8"。实测跑出 **13 / 15**,没过。

**那个 8 是我拍的,没有推导** —— 此刻最容易做的事是把 8 改成 16 让它变绿,
而那正是 CLAUDE.md 骂的「结果出来之后再定标准,人必然会挑一个刚好能通过的标准」。

正确的改法是回到需求本身的单位(§1.1 Q2 讲的是**队列被挤爆**):

|---|---|---|

| 08-19 加节流 | **5** | ✅ 余量 15 |
| 08-20 现状 | **25** | 🔴 溢出 |
| 08-20 加节流 | **7** | ✅ 余量 13 |

⭐ 这个量法顺带**独立复现了 08-14 那次事故**:现状确实会越过 20 格,
而那天实际丢弃 41 条。判据里的红线常量直接 `import alerts.PENDING_MAX`,不另抄一份。

判据同时断言「**现状必须越线**」—— 否则这条判据会跟着永远绿,什么都没验。

### R1 🔴 已修 — 我在 §2.7 写的安全承诺是**假话**

> 原文:「冷却状态丢失(文件损坏/被删)会退化成"立刻推一条",不是静默。方向是安全的。」

`cycle_state.read_state` 只捕 `(OSError, JSONDecodeError, KeyError, TypeError)` ——
它挡的是"读不出来"。**"语法合法但形状不对"会被原样返回**,然后 `throttle` 直接崩。
我造真坏输入实测(不是推的):

| 磁盘上的内容 | 结果 |
|---|---|
| `{"throttle": "garbage"}` | 💥 `AttributeError` |
| `{"last": "oops"}` | 💥 `ValueError` |
| `{"last": [1,2]}` | 💥 `TypeError` |
| `{"suppressed": "oops"}` | 💥 `ValueError` |

**三个不同的异常家族** —— 与 2026-08-17 pyarrow 那次(`ArrowInvalid`→ValueError /
`ArrowTypeError`→TypeError / `ArrowIOError`→OSError)是同一个形状。

⭐ **放大效应(这才是它值 BLOCKER 的原因)**:`run_cycle.main` **零 try/except**,
且心跳写在告警**之后** ⇒ 崩一次**整轮心跳都不写**,看门狗会报"采集器死了",
而轮询/结算其实全都成功了 —— 一次"记账最后一步摔了"被误读成"整轮没跑"。

### R2 🔴 已修 — 「先写状态再 dispatch」的理由是我编错的

我在代码注释里写过:*"先落状态再 dispatch:被杀时状态没写 ⇒ 下一轮当成第一次再推一条,
防洪在最需要它的时刻失效。"* **这个理由是错的。**

实际:`dispatch` 里 `items.append` 只在**内存**,只有 `_send` 返回 `False` 之后才落队列文件。
进程若在 `_send`(最坏阻塞 30s)期间被 SIGTERM 杀掉,那条消息**既没发出去、也没进队列** ——
彻底丢失。而冷却已经提前记下 ⇒ 同一个 key 被压住最长 3 小时。

⭐ 最扎的是它**恰好打在 `offset_overflow_warm` 上** —— 今天上午刚核实过,
那是唯一被证明与**永久数据丢失**挂钩、且 6/6 全部真发出去过的告警。
它原先是**每轮无条件推**,丢一次下轮自愈;这次改动把那个隐性保证悄悄作废了。
而 SIGTERM 最可能发生的工况(网络退化、周期被拖到接近 900s 预算),
正是它最该响的时候 —— **旧的保证在新工况下变成假话**,第 4 条又中一次。

修法:冷却状态改到 `dispatch` **之后**落盘。被杀 ⇒ 两边都没发生 ⇒ 下一轮重推,自愈保持。
防洪也没打折:丢掉的消息根本没进队列,不会撑大它。

### R3 🔴 已修 — 时钟前跳后被纠正,会把某个 key 卡死 116 天

(`run_cycle.py` 的注释),而 `throttle` 用的恰是 wall clock。
修法:`now <= prev` 视为状态不可信 ⇒ 放行并覆盖。
