量化研究手记 · Field Notes · 三部曲 之二

去官方要数据的路上，我撞见了更要紧的事

本来只是个补数据的苦力活：我们只有两个月历史，去官方接口多拉一点。结果历史拉到了十四个月——顺手却发现，我们的回测一直在自己给自己批卷子。这篇讲工程，也讲三次被自己拦下的经过。

主题 Polymarket · 官方 API 回填 · 数据口径 日期 2026-07-15 系列 三部曲之二(共三篇)

00前情

一个薄薄的希望，和一个明确的瓶颈

上一篇的结局：我们找到了项目第一个通过全部红线的净正候选——利用"长热偏差"买热门那一侧，净收益 +0.46%，胜率 92%。

但它有个说不过去的软肋：只有两个月数据。而且半凯利仓位那次模拟甩出 90% 以上的回撤，把"需要更多历史"从可选项顶成了前提。

所以今天的任务清单本来很朴素，就两条：

  • ③ 精炼甜区——把"最肥的那段价格区间"单独拎出来测（干净、快）；
  • 并行：从 Polymarket 官方接口重拉历史价，彻底解决数据浅的问题。

我把顺序调了一下：先探 API。理由是——精炼甜区跑在同样那两个月数据上，只会让数字更好看，不会让我们更有把握；而 API 探测是决定性的，如果能拉到更长的历史，甜区就该直接在长历史上测一次，而不是先在浅数据上测一遍、回头再测一遍。探不通，也只损失二十分钟。

01三个坑

探路：二十分钟，踩了三个坑

坑一：机器的 IPv6 是坏的

第一个请求就报错：Name or service not known——查无此域名。但奇怪的是 getent 明明解析出了地址。

真相是：这台机器的 DNS 只返回 IPv6 地址，而它的 IPv6 根本连不出去。Python 默认优先走 IPv6，于是撞墙；curl -4（强制 IPv4）却一切正常。所有拉数脚本必须强制 IPv4。

坑二：已结算的市场，默认查不到

更隐蔽。我按 slug（市场的唯一名字）去查，一半查不到。一开始以为是官方没有这些市场的记录。

其实是查询姿势不对：Gamma 接口默认只返回"还在交易"的市场，已经结算归档的，必须显式加 &closed=true 才给。而我们要的恰恰是已结算的——不然没有正确答案。

坑三：我抄了截断的输出

这个纯属自己蠢，但值得记：调试时我从终端输出里手抄 slug 去验证，抄的却是被截断到 46 个字符的版本，于是"查不到"。这个坑我一天内踩了两次，第二次还差点误判成"代码改坏了"。

教训 · 调试时的自我怀疑

第二次踩坑时，症状是"我刚改完代码，功能就坏了"——几乎所有直觉都指向"改错了"。但真凶是测试数据本身是假的。

值得记住：当"我刚动过的地方"和"出问题的地方"重合时，那种因果关系的诱惑力极强，强到让人不去检查更蠢、更基础的可能性。

02好消息

坑填完，收获比预期大得多

接口通了之后，结果远超预期。原计划是"回填到三月"，实际拿到的是：

而且官方直接给权威的结算结果——这个市场最终是"是"还是"否"，白纸黑字，不用猜。

这句话当时听着只是个附带好处。它其实是整个故事的转折点。

03转折

等一下——我们原来是怎么知道"谁赢了"的？

拿到权威答案之后，一个我从来没问过的问题自然浮了上来：在没有权威答案的这几个月里，回测是怎么判断"这个市场结束了没有、谁赢了"的？

翻开代码（engine/data.py:81），答案让我坐直了。它自己猜，靠一条土规则：

看最后一张价格快照。如果价格接近 0 或接近 1，就认为这市场已经结束了。

这条规则的道理听起来是对的：市场真结束时，答案要么发生要么没发生，价格必然砸向 0 或 1，不可能停在中间。这叫"收敛"。

我拿官方答案对了一下这条土规则。结果是两句话：

  • 好消息：它判胜负从不出错。只要它说某个市场结束了、某边赢了，官方都印证是对的。
  • 坏消息：它静默丢掉了大量已结算的市场。丢掉的，正是那些终值价没收敛的盘。

为什么会漏？想象一场网球赛，我们唯一那张价格快照拍在比赛打到一半的时候，价格 0.62。比赛后来打完了，官方早就结算了。但对回测来说，"最后一张快照"就是这张 0.62——不接近 0 也不接近 1，不收敛，于是判定："这市场还没结束"，丢掉不用。

可它明明早就结束了。我们只是没拍到结束那一刻而已。

04为什么这要命

丢掉的，恰好是我们该亏钱的那些

如果丢的是随机一批，那只是浪费数据，不致命。但它丢的不是随机的：

它专门丢掉"价格停在中间就结束了"的盘。

而"价格停在 0.62 却最终输了"的盘是什么？正是我们这个"买热门那一侧"的策略该亏钱的案例。

比喻 · 自己批自己的卷子

一个学生自己批自己的卷子，规则是"看不清答案的题就跳过不算分"。结果他跳过的全是自己不会做的题，最后算出个 92 分。

那 92 分不是他的水平，是规则送的。

我们那个 +0.46% 的净利、92% 的胜率，此刻高度可疑：它可能是靠自动跳过自己的败绩考出来的。

于是当天的计划整个翻了。原定"先精炼甜区"——推迟。理由很简单：

在一个有选择偏差的样本上精炼甜区，只会把偏差磨得更锋利。

而验证这个怀疑，根本不需要更多数据，只需要把"自己猜"换成"问官方要答案"。这比补数据更便宜，也更致命。

05三次自我拦截

写回填工具的路上，我被自己拦下三次

接下来是苦力活：把所有相关市场从官方接口拉一遍。但这个"苦力活"里，有三次差点酿成假结论。

第一次：代码审查拦下一个会毒化数据的缺陷

按项目规矩，网络代码写完必须过一遍审查。审查揪出一个我完全没意识到的问题：我的代码把"官方确认没有这个市场"和"网络抖了一下没拿到"返回了同样的结果。

后果是：一次网络波动，会让一个真实市场被永久记成"不存在"，而断点续跑时又会跳过它——再也不会重试。跑上万个市场、几十分钟、对着一个已知偶发故障的接口，这必然会静默污染数据。

（另一个：某类网络异常不属于我捕获的类型，读到一半断线会直接打死整批任务。）

第二次：我选错了市场范围，覆盖率只有 8%

这次是我自己发现的，也最惊险。我按"快照数 ≥ 8"筛选要抓的市场，抓了 2436 个，自我感觉良好。

直到我去数了一下真正需要的市场集有多大——9858 个，而我抓的 2436 个里只有 767 个在里面

覆盖率 8%。原因是那 9858 个候选里，有 4196 个在库里只有一张快照——监控只瞄到过一眼，但那一眼正好落在入场窗口里，所以它们是完全合法的样本。按快照数筛选，恰好把它们全部排除。

如果这样跑下去，测试会变成"真值口径"和"市场范围"两个变量一起动，测了等于没测。

第三次：手写 SQL 和引擎规则差了 5 个市场

我写了段 SQL 来筛市场，跟引擎的规则一对，差 5 个（9859 vs 9858）。数量上无关紧要，我知道原因（引擎会丢弃同日重复的快照，而且某些日期格式解析成空）。

但"数据管线上差不多就行"正是以后咬人的地方。与其去对齐两套规则，不如让回填直接调用引擎自己的规则——从构造上就不可能漂移。改完，差异归零。

规律 · 三次拦截的共同点

回头看，这三次拦下的都不是"代码跑不起来"的错误——三个版本都能跑，都能出数字，而且数字看起来都很正常。

它们全是"能跑通、但结论是假的"那一类。这类错误没有报错信息、没有崩溃、没有红色警告，只有一个看起来挺合理的数字。这也正是这个项目为什么要预登记、要审查、要闸门——不是流程洁癖，是因为这类错误只能靠制度挡，靠不了眼力和运气。

06一个反直觉的判断

"Yes"这个词，其实是个误称

还有一个坑值得单独讲，因为它的结论是反直觉的。

审查提醒我：代码假设官方返回的第一个选项永远是"Yes"。我去查了一下——已结算市场里只有 54% 是 ["Yes","No"]，其余是 ["Long","Short"]、球队名、党派名。对它们取"第一个选项赢没赢"，含义完全不同。

更麻烦的是：我们库里 10 万行价格，一律标着 outcome='Yes'，不管这市场到底是不是"是非题"。那么库里的"Yes 价"到底对应官方的哪一侧？没人知道。

这是可以实测的。拿库里的价和官方的价在同一天对表，就知道是不是同一侧。结果：

看懂这张图就明白了：如果下标真的反了，数据越多应该越确信是反的，而不是越接近零。所谓"反向"的那些，全部集中在只有一天重叠的盘上——尤以当天开打、当天结束、盘中价格剧烈波动的网球赛为甚。拿一个盘中快照去比日收盘价，本来就不可靠。

而重叠 ≥3 天的 346 个市场，100% 对齐，偏差中位数 0.0000（逐位精确相等）。

这里有个反直觉的结论，我想强调：正确做法是"不剔除"。如果我按"反向"去剔掉那 45 个市场，我剔掉的其实是波动最大的市场——那才是真给结果引入偏差。我最后只保留了一个全局闸门：重叠≥4 天的市场对齐率必须 ≥95%，否则脚本直接中止、不出结论。

洞察 · 标签不重要

更深一层：这个策略本来就跟标签无关。它做的是"买标价高的那一侧"——那一侧叫 Yes 还是 Long 还是 Canadiens，根本不重要。重要的只有一件事：价格和结算，指的必须是同一侧。这一点已经验证成立。
