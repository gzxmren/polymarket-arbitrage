# 采集器监控设计:先找读者,再造仪表

**日期**:2026-08-17
**状态**:设计稿,等用户拍板后才动手(四步流程第 2 步)
**起因**:用户问「是不是需要一个后台脚本时时刻刻监控采集器/日志/判据?再在已有 dashboard 里做个可视化报表?」

---

## 这份文件是干什么的

回答上面那个问题。但在回答"做什么"之前,先回答一个更要紧的:
**这个项目已经建过一次监控报表,它现在是死的,而且没人发现。** 不先搞清楚它是怎么死的,
新造的那个大概率同样下场。

本文所有数字都是 2026-08-17 当天实测跑出来的,不是回忆。

---

## 先说人话:三句话结论

1. **不是"缺报表",是"缺读者"。** 让今天这个 bug 暴露的那份数据,已经在心跳里躺了 9 天,
   每 15 分钟写一条,一个读取者都没有。
2. **推 > 拉。** 需要人主动打开的东西,在这个项目里的存活率是 0/1。自己找上门的
   (Telegram 告警)是唯一被证明活着的通道。
3. **网页排最后,而且可能根本不需要。** 先让日报跑两周;如果两周里你一次都没想点开看细节,
   那就省下那 4 小时。

# 第三部分:设计原则(四条,每条都有事故背书)

## 原则一:推,不是拉

**依据**:这个项目里,需要人主动打开的东西存活率 0/1(dashboard 死 26 天无人知);
自己找上门的东西(Telegram 告警)是唯一被证明还活着的通道。

**所以主界面不是网页,是每天固定时间推一条日报。** 短到能在手机锁屏上读完:

```
📊 采集器日报 08-17(第 42 期)
腿1 成交流   ✅ 54.7 万笔 / 96 轮 / 最慢 282s
腿2 结算真值 ✅ 5,072 个 / 零流最长 3 轮
腿3 注册     ✅ 涌入 7,412 全部登记,丢弃 0
腿4 回填     ✅ 剩 70 个
判据 568 绿 / 数据体检 ✅
昨日无异常
```

关键在最后一行。**稳态就是一句"无异常"**,平时无聊到三秒扫完;
一旦某行变红你会立刻停下 —— 这才叫有分辨力。

## 原则二:三类信号分开报,绝不合成"健康度"

**依据**:08-13 那天如果有个综合健康分,它会是绿的 —— "活着"和"数据对不对"两项都正常,
只有"干活了吗"塌了。三项一平均,故障就被稀释掉。
(同 CLAUDE.md:独立链路分开判定,不许相加。)

| 类别 | 问的是什么 | 现状 |
|---|---|---|
| **活着吗** | timer 在跑?心跳新鲜? | ✅ 看门狗已覆盖 |
| **干活了吗** | 每条腿的产出计数、连零轮数 | 🔴 **08-13 漏掉的就是这一类,必须补** |
| **数据对吗** | 判据绿红、数据体检 | 🟡 判据有,但没进任何日常视野 |

## 原则三:不新建任何数据管线,只做读者

**依据**:三月那个 dashboard 死掉的直接原因是**数据源搬家了而它不知道**
(`07-data` 停写 26 天)。

心跳已经是一份现成的时间序列:**55 字段 × 3,010 个文件 × 27 个日分区**,
append-only,采集器每轮自己写。日报和报表都只做它的**读者**。

⛔ 明确不做:不新建采集路径;不碰 SQLite 那条同步链
(`data_sync.py` 和 `data_sync_v2.py` 两份实现权威不明);不复活 `07-data` 依赖。

⭐ 并且要有一条判据把"读者读的正是采集器写的那份"焊死 ——
形式照抄今天给批量开关加的那条(部署单元里没打开就变红)。

## 原则四:这个监控自己会不会静默死掉?

把核心问句对准监控本身:**「如果日报明天不发了,我看到的会有什么不同?」**
答案若是"没有不同",它就是第二个 dashboard。

**不能再新建一个盯梢的**(无限套娃)。正解是接到已被证明活着的东西上:

1. 采集器每次推完日报,在心跳里记一个 `digest_sent_at`
2. **已经每 30 分钟跑一次的看门狗**顺手检查这个时间戳是否超过 26 小时

不加新组件,只加一个字段 + 一个判断。看门狗有 systemd timer 兜底、今天验证过健康。

## 原则五(防洪):日报和告警必须走两条路

**依据**:08-03 那次同期推了 1340 条告警,**没有一条指向真正出事的那件事**。
噪音会让真信号无处可显。

- **告警** = 事件驱动,稳态**零条**。红线不变,不许把日报塞进这个通道。
- **日报** = 每天一条,稳态也会发(内容是"无异常")。这是它的功能,不是噪音 ——
  但正因如此,它绝不能和告警混在一个心智通道里。

# 第四部分:具体做什么

先过项目最高原则那一问:**它离赚钱有多远?**

老实说:**这一整块都是手段,不是目的。** 唯一有硬理由的是第 1 件 ——
08-13 真的永久丢了约 1.4 万笔成交,而看门狗全程零红灯。其余两件是"防止下一次",
理由较软,所以排后面、而且可以砍。

| # | 做什么 | 代价 | 不做会怎样 |
|---|---|---|---|
| 1 | **补看门狗的空转红线** | ~0.5h | 🔴 下次网络断,再丢一次数据,仍然零告警 |
| 2 | **每日推送日报** + 防它自己静默死掉的时间戳 | ~1.5h | 🟡 心跳里 25 个字段继续没人看;下一个"9 天没人发现"的问题照旧 |
| 3 | 网页报表(只读心跳,单页) | ~3-4h | 🟢 需要看趋势时得手工写 SQL |

**建议:先做 1 和 2,第 3 件等日报跑两周再定。**
判据很简单 —— 如果这两周里你一次都没有因为日报里某一行想点开看细节,
那就说明网页确实不需要,省下 4 小时。

## 4.1 第 1 件的做法(看门狗空转红线)

现在的 `collector_watchdog.py` 只有三条 🔴:timer 不 active / 无心跳 / 心跳超 40 分钟。
08-13 那 13.5 小时**一条都没碰到** —— 每轮都跑完了,心跳准时,只是内容全是 0。

它唯一的反应是一条 🟡:「最近一轮 firehose 抽风(采样 0 笔),**若持续**须查接口/IP」。
"若持续"三个字后面**没有接任何东西** —— 没有计数器在数它持续了几轮。

**要加的**:一条"连续 N 轮产出为 0"的 🔴,且必须分开
「有活没干成」(异常)与「没活可干」(正常)。判据先写,并且先在一条
"全 0 但新鲜"的假心跳上跑,确认现在的 `check()` **不**报红 —— 不这么做,
新判据可能同样没有分辨力。

## 4.2 第 2 件的做法(日报)

- **数据源**:只读 `11-collector/data/audit/**/*.parquet`(心跳),外加 pytest 退出码
- **触发**:独立 systemd timer,每天固定时间一次(Persistent=true 防 suspend 漏跑)
- **通道**:复用 `alerts.py` 已有的 Telegram 发送 + 待发队列(它在 08-13 断网 458 分钟后
  成功补发过,是被验证过的)
- **内容**:上面那个模板;每条腿一行;末行是判决
- **自保**:写 `digest_sent_at` 进心跳,看门狗查它是否超 26 小时

⭐ 日报的字段选择顺便解决孤儿问题:**每一个进日报的字段,就此有了读取者**;
没进日报又没有其它读者的字段,应当被质疑是否该留在心跳里。

# 第五部分:本设计**不能**回答什么

- **不回答"日报里该放哪些阈值"。** 阈值必须有实测分布支撑(CLAUDE.md F2),
  而日报第一版应当**只报数字不报判决**,攒够两周分布再定红线。
  先定阈值 = 在没有分布的情况下拍脑袋,那正是本项目反复犯的错。
- **不回答"网页该长什么样"。** 那取决于日报跑两周后你真正会去下钻的是什么,
  现在设计等于凭空猜。
- **不回答"要不要救三月那个 dashboard"。** 我的倾向是不救(数据源已废、
  同步链两份实现权威不明、端口被别的项目占),但这是笔账,不是判据,
  等真要做第 3 件时再算。
- **不承诺"以后不会再有静默失败"。** 本设计只把**已经知道的**那一类
  (产出为 0 但进程正常)接上读者。新形状仍会出现。

## 附:验收判据草案(动手前会先写成可执行的)

| # | 判据 | 先红后绿的验法 |
|---|---|---|
| P1 | 喂一条"全 0 但时间戳新鲜"的心跳,`watchdog.check()` 必须报 🔴 | 在今天的代码上跑 → 必须绿(证明现在是瞎的) |

| P5 | 日报连续 3 天稳态 → 告警通道零条(防洪) | 稳态静默这一头 |
