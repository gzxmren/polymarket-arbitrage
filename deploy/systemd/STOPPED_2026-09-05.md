**别照 `README.md` 把下面这 6 个 timer 装回来** —— 它们是**有意停的**,不是漏装。
要恢复请先读本文件末尾的「怎么恢复」。

## 停了什么

| timer | 原本干什么 |
|---|---|
| `polymarket-rebirth-collector` | 主采集器(每 10 分钟一轮:发现+轮询+结算守望+compaction) |
| `polymarket-collector-watchdog` | 采集器看门狗(采集器停后它会每轮报红,故必须一起停) |
| `polymarket-backfill-closed` | 已关闭市场成交回填清扫 |
| `polymarket-market-times` | 时间防火墙侧表回填(**活已干完**:覆盖 99.9915%) |
| `polymarket-daily-digest` | 每日日报推 Telegram |
| `polymarket-slippage-probe` | H6 滑点探针(**H6 已于 2026-07-15 证伪**,已白跑近两个月) |

停法:`systemctl --user disable --now <timer>`(**disable**,机器重启也不会复活)。
**unit 文件本身全部保留**(本机 + 本目录),判据仍在守它们的内容一致性。

## 为什么停

方向三(跟单领先者)于 **2026-09-04** 判决 `NOT_FOLLOWABLE`,已关闭。
**没有任何活着的方向需要「新增」的事件盘成交数据** —— 项目资源已转向 BTC 短周期盘方向。
判决与依据:`docs/DESIGN_CLOSE_DIRECTION3_2026-09-05.md`。

## 🔴 停采期间会永久丢什么(实测,别乐观)

| 类别 | 能不能补 |
|---|---|
| 已知市场,笔数 < 1 万(**99.92%**) | ✅ 可完整回填(`trades?market=<cid>` offset 上限 1 万笔够得着) |
| 已知市场,笔数 ≥ 1 万(**213 个**) | ⚠️ 只能补最后 **0.2~40.8 天**(中位 2.1 天)⇒ 按笔数上界丢 14.71%、金额 9.40% |
| **停采期间新诞生的市场** | 🔴 **100% 永久失明** |

**最后一行是真正不可逆的那条**:发现新市场的唯一路径是采集器实时采样全局成交流
(`discovery_service.py::sample_firehose()`),全项目**没有**按日期枚举 Gamma 市场的备用路径。
⇒ 停采期间创建并结算的市场,我们连它的 `condition_id` 都不会有,`offset` 能回溯多久与它无关。
⛔ 这是**已知且被接受**的代价(2026-09-05 用户拍板「彻底 close」),不是遗漏。

## 怎么恢复

```bash
systemctl --user enable --now polymarket-rebirth-collector.timer
systemctl --user enable --now polymarket-collector-watchdog.timer
systemctl --user enable --now polymarket-backfill-closed.timer
# 侧表/日报/滑点探针按需,前两个是主链路
```
恢复后若要补停采期间的历史,从上面「湖内最后一笔成交」那个时间戳往后补,
并**明确接受**新生市场那一段的永久缺口(它会成为分析窗口的一条硬边界,
按项目铁律必须当作**带日期的口径变更**记录下来)。
